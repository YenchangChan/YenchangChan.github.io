# 扩容之后为什么不自动做数据均衡

> 「ClickHouse 扩容不会自动均衡数据，Doris 会，所以 Doris 更成熟。」
>
> 这句话我听过很多次。它的前半段是事实，后半段是误读。
>
> **真正的差异不是成熟度，是两者对「sharding 所有权」的假设不同。** 而一旦把这个假设看清楚，你会发现自动均衡在 ClickHouse 上不是「做不做得到」的问题 —— 是做了就会错，而且是**静默地错**。

## 一、先承认事实

ClickHouse 扩容之后，老数据不会自己搬到新节点上。新写入的数据按新的分片规则走，老数据原地不动，于是集群长期处于不均衡状态。

Doris 扩容之后，BE 之间会自动做 tablet 迁移，最终收敛到均衡。

**这两句都是真的。** 问题只在于从这里推出「所以 Doris 更成熟」。

## 二、差异在于：谁拥有 sharding 规则

**Doris 的分桶规则由引擎自己管。** 建表时声明 `DISTRIBUTED BY HASH(k) BUCKETS n`，引擎知道 hash 函数、知道分桶数、知道每一行属于哪个 bucket。**引擎掌握全部语义，所以它搬数据是安全的** —— 它能算出搬完之后每一行还在正确的位置。

**ClickHouse 的 sharding 常常由业务在写入端自己决定。**

以我维护的 [clickhouse_sinker](https://github.com/housepower/clickhouse_sinker) 为例，路由规则是写入侧的配置：

```go
// 未指定 shardingKey：按 Kafka offset 均摊
shard = int(msg.Offset >> offShift) % shards

// shardingKey 是数值类型
shard = int((val64 / policy.stripe) % uint64(policy.shards))

// shardingKey 是其他类型
shard = int(xxhash64(val64) % uint64(policy.shards))
```

注意这三条公式里都有 `shards`，而且**它们跑在 ClickHouse 之外**。

ClickHouse 服务端从头到尾不知道这些规则的存在 —— 它只看到一批批数据落到了本地表上。**它没有任何办法反推出「这一行为什么在这个节点」。**

这不是能力差距。**Doris 把 sharding 收进了引擎，ClickHouse 把它留给了使用者。** 两种设计各有代价，而自动均衡能不能做，是这个选择的直接后果，不是成熟度的度量。

## 三、所以自动 rebalance 不是「能不能」的问题

### ① 有些数据按业务语义 sharding，自动搬迁会让数据错

最直接的例子是去重。

`ReplicatedReplacingMergeTree` 的去重作用域是**单个分片内**：同一个 key 的多行，只有落在同一个分片上才会被 merge 掉。**分布在不同分片上的重复行，Replacing 永远不会去掉它们。**

所以用这个引擎的表，写入侧必须把去重字段设成 `shardingKey`，保证同一个 key 恒定路由到同一节点。

现在让存储层自动 rebalance：它按容量把 parts 搬到新节点上，**同一个 key 的数据被打散到了两个分片**。

去重从此失效。

同类的还有：按业务 id sharding 以便聚合查询本地化、按 join key sharding 以便把分布式 join 优化成本地 join —— **搬完之后这些前提全部不再成立。**

### ② 而且是静默地错

这才是真正要命的部分。

搬迁不报错，写入不失败，查询照常返回结果。`SELECT count()` 变多了一点 —— 但谁会天天盯着 count？聚合结果偏了一点 —— 但你没有一个「正确答案」可以对照。

**没有任何一个信号告诉你它从哪一天开始错的。**

等到有人发现对不上，你要回溯的是：哪次扩容、搬了哪些 part、影响了哪些 key、错了多久。而这些信息，在一次「自动」完成的操作里通常没有留痕。

### ③ 最关键的一层：做决定所需的信息，不在做决定的那一层

前两条还只是「有风险」，这一条说的是**这个能力在架构上就不成立**。

存储层看得见的东西是：parts、分片、磁盘占用、行数。

存储层看不见的东西是：**这张表的 sharding 有没有业务语义**。

所以它永远无法判断「这次搬迁安不安全」—— 不是判断得不够准，是**判断所需的输入根本不在它的视野里**。

::: warning
这不是实现得不够好，再怎么优化也解决不了。

一个组件被要求做一个它拿不到充分信息的决定时，
它能做的只有**猜**，然后把猜错的代价转嫁给使用者。
:::

Doris 之所以能做，恰恰是因为它把 sharding 规则收进了引擎 —— **它做决定所需的信息，就在做决定的那一层。**

## 四、即使在语义安全的场景，我也不自动做

上面说的是「不得不」。这一节说的是「即使可以，我也不」。

有些表确实没有业务语义上的 sharding —— 默认按 offset 均摊的那种。理论上搬它们是安全的。

**我还是不做成自动的。**

因为**数据搬迁是不可逆的**。搬完之后你没有 undo。而一旦出问题，运维需要回答三个问题：

- 搬了什么
- 搬到哪里
- 搬之前是什么样

自动化的操作天然不产生这些记录 —— 它的设计目标恰恰是让人不必知道这些。

在金融环境里这条更硬：**每一步改变数据分布的操作都要可审计、可追溯，不能是黑盒。** 不是流程上的繁文缛节，是出事之后你得有东西可查。

> 顺序上我把这一节放在第三节后面，是有意的。
> 第三节是普适的技术论证，跟行业无关；
> 这一节是我自己的取舍。**把取舍放在论证前面，容易被读成行业包袱。**

## 五、所以 ckman 是怎么做的

**能力提供，但由人触发。**

[ckman](https://github.com/housepower/ckman) 里有数据均衡功能 —— 扩容之后确实需要它，尤其是改了分片数、存量数据需要 rehash 的时候（这本身就是个很重的操作）。

但它的形态是：

```
前置检查   →   执行计划预览   →   风险确认   →   执行
```

- **前置检查**：集群状态、磁盘余量、是否有正在进行的 merge
- **执行计划预览**：这次要搬哪些 part、从哪到哪、搬完之后各节点什么样
- **风险确认**：明确告诉你这个操作不可逆

**不是「点了就跑」，是「看清楚再点」。**

差别在哪？自动均衡把决定权从人手里拿走了；ckman 把决定权留给人，**只是把做决定需要的信息摆到他面前**。

而人恰好拥有存储层没有的那个信息：**这张表的 sharding 有没有业务含义。**

## 六、一条可推广的原则

::: tip
**技术上可做 ≠ 应该做。**

当做一个决定所需的信息，不在做决定的那一层时，自动化就是在赌。

而这一类赌局有个共同特征：**赢的时候你不知道，输的时候你也不知道** ——
它不会报错，只会让结果慢慢偏掉。

遇到这种情况，正确的做法不是把自动化做得更聪明，
是**把信息补给那个真正有判断力的人，然后让他按按钮**。
:::
