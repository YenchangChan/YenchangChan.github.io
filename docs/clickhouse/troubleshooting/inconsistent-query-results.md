# 同一条 SQL 每次查出来不一样：先看它是怎么变的

> 「数据一会儿有一会儿没有」「同一条 SQL 多次查询结果不一样」—— 这是我被问得最多的 ClickHouse 问题之一。问的人里有刚上手的，也有做了很多年数据的。
>
> 我遇到过的原因有四种，彼此毫不相干。但它们**让结果变化的方式**不一样，所以排查不用从四个原因挨个试起 —— 先看清结果是怎么变的，通常就能确定是哪一种。

## 一、先问两个问题

1. **偶发还是必现？** 连续查十次，是每次都可能不同，还是偶尔才不同？
2. **怎么变？** 在几个固定值之间来回跳；朝一个方向慢慢收敛；还是先有、后没有、再也不回来？

| 结果的变化方式 | 最可能的原因 | 第几节 |
|---|---|---|
| 在**几个固定值**之间来回跳，过多久都不收敛 | 副本之间数据根本不一致 —— 引擎或集群配置错了 | 二 |
| 来回跳，但**过一阵自己收敛**到一个值 | 副本同步延迟 | 三 |
| 不跳，但**单调变少**，最后稳定 | 去重引擎还没合并完，查询没加 `FINAL` | 四 |
| **先查得到，后来查不到**，再也不回来 | TTL 把数据删了 | 五 |

第一条最常见，也最需要尽早发现 —— 它不会自己好。

## 二、副本之间根本不一致

### 现象

假设 2 分片、每分片 2 副本，副本之间**没有同步**，某张表的数据分布如下：

```
          分片 1                     分片 2
   副本 1      副本 2         副本 1      副本 2
   [1, 3]      [2]            [6]         [4, 5]
```

分布式表查询时，在每个分片上选一个副本。于是查询结果有四种可能：

| 选中的副本 | 结果 |
|---|---|
| 分片 1 副本 1 + 分片 2 副本 1 | 1, 3, 6 |
| 分片 1 副本 1 + 分片 2 副本 2 | 1, 3, 4, 5 |
| 分片 1 副本 2 + 分片 2 副本 1 | 2, 6 |
| 分片 1 副本 2 + 分片 2 副本 2 | 2, 4, 5 |

**结果在有限的几个值之间跳，怎么等都不会收敛** —— 这就是第一节表里第一行的那种变化方式。

### 原因：`internal_replication` 和表引擎要配对

副本之间同步数据，靠的是 `ReplicatedMergeTree` 通过 Keeper 做复制。集群配置里 `<internal_replication>` 决定的是另一件事：**通过分布式表写入时，数据写到分片里的一个副本，还是所有副本**。

| `internal_replication` | 表引擎 | 结果 |
|---|---|---|
| `true` | `ReplicatedMergeTree` | ✅ 分布式表写一个副本，引擎负责复制到其他副本 |
| `true` | `MergeTree` | ❌ 只写进一个副本，**没有任何机制同步**。就是上面的现象 |
| `false` | `MergeTree` | ⚠️ 分布式表自己往每个副本各写一份；某个副本写失败时，副本之间就会悄悄不一致 |
| `false` | `ReplicatedMergeTree` | ⚠️ 分布式表写了所有副本，引擎又复制一遍，可能重复写入 |

生产环境绝大多数人会把 `internal_replication` 设成 `true`（这也是 ckman 的默认配置），所以**最常见的组合就是第二行：配置是对的，建表用了 `MergeTree`**。

### 确认

不要通过分布式表查，直接看每个副本各有多少：

```sql
SELECT hostName() AS host, count()
FROM clusterAllReplicas('<cluster>', <db>.<local_table>)
GROUP BY host ORDER BY host;
```

同一个分片内的副本行数不一样，而且长时间不一样，就是这个问题。再看建表语句的引擎确认。

### 修复

**数据不多、或者源头还能重导**：删表，用 `ReplicatedMergeTree` 重建，重新导入。最快也最安全。

**数据多、源头已经没了**：

- **建 `ReplicatedMergeTree` 临时表，`INSERT ... SELECT` 搬过去，再 rename。** 单节点每秒百万行量级，通常可以接受。
- **`MOVE PARTITION TO TABLE` 不行。** 它要求源表和目标表属于同一个引擎族（都是 replicated 或都不是）。
- **`ATTACH TABLE ... AS REPLICATED`** 可以把一张 detach 了的 `MergeTree` 原地转成 `ReplicatedMergeTree`，较新的版本还支持在数据目录里放一个 `convert_to_replicated` 标志、重启时自动转换。

后两种原地转换方式都有一个前提，官方文档写了，但很容易被跳过：**如果不同副本上的数据不同，要先同步，或者在除了一个副本以外的所有副本上删掉数据。** 你遇到这个问题，恰恰就说明各副本的数据**已经不同了** —— 所以原地转换之前，先决定以哪个副本为准，或者先把各副本的数据合并到一处。直接在每个副本上原地转换，各副本带着各自的数据进入复制，结果不会是你想要的。

## 三、副本同步延迟

配置和引擎都对，但结果还是来回跳 —— 区别在于**过一阵会自己收敛**。

同样 2 分片 2 副本，数据都写进副本 1，两个分片的副本 2 都落后：

```
          分片 1                     分片 2
   副本 1      副本 2         副本 1      副本 2
   [1, 2, 3]   [1, 2]         [4, 5, 6]   [4]
```

四种组合查出来是 `1–6`、`1,2,3,4`、`1,2,4,5,6`、`1,2,4` —— 也在跳，但副本 2 追上来之后，四种组合会收敛成同一个结果。

### 确认

```sql
SELECT database, table, replica_name, absolute_delay, queue_size, inserts_in_queue
FROM system.replicas
WHERE absolute_delay > 0 OR queue_size > 0;
```

`absolute_delay` 持续很大、`queue_size` 不降，就是副本追不上。再看 `system.replication_queue` 里卡住的条目和 `last_exception`。ckman 的复制表状态页面里，同步进度长期低于 80% 的副本，八成有问题。

同步跟不上，通常和两件事有关：**Keeper 的健康状态**，和**拉取线程池的大小**（`background_fetches_pool_size`）。

分布式查询本身也有一道保护：副本延迟超过 `max_replica_delay_for_distributed_queries`（默认 300 秒）时，会优先避开这个副本。所以延迟很小时你可能看不到跳动，延迟很大时反而可能被这道保护掩盖 —— 要确认，还是直接查 `system.replicas`。

## 四、去重引擎，没加 `FINAL`

不跳，**单调变少**，最后稳定在一个值。

`ReplacingMergeTree` 按 `ORDER BY` 的键去重，但去重发生在**后台 merge 的时候**，而 merge 的时机不确定。查询时看到的是「部分合并」的状态：有的重复已经合掉了，有的还没有。一边写一边查，merge 在持续发生，每次查到的都是一个不同的中间状态。

`count()` 会随着 merge 推进慢慢变少；按非去重键查某个字段，同一个 key 可能一会儿出现多次、一会儿只出现一次。

需要查到最终状态时，加 `FINAL`：查询时在读取阶段完成去重（不会把合并结果写回磁盘）。代价是查询变重 —— 这是另一个话题。

还有两条容易漏掉的边界：

- **merge 不跨分区**。去重键相同、但落在不同分区的两行，后台 merge 永远不会把它们合掉。
- **`FINAL` 不跨分片**。分布式表上的 `FINAL` 是在各分片内各自做的；去重键相同的两行如果落在不同分片，`FINAL` 也去不掉。**分片键必须包含去重键**（或由它决定），否则这个问题无解。

## 五、TTL：先有，后没有

最难查的一种，因为它看起来像丢数据。

表设了 TTL，比如保留 1 个月。但写进来的数据不规范 —— 混着一年前、甚至几年前的存量数据。这些数据刚写进来时查得到；等到 TTL 生效，就被删了，再也不回来。如果这种存量数据在**持续写入**，看起来就是「一会儿有一会儿没有」。

TTL 删除不是写入时立即生效的，而是在后台 merge 时执行。带 TTL 的 merge 还有频率限制：`merge_with_ttl_timeout`（默认 4 小时）控制同一分区两次 TTL merge 之间的最小间隔。所以**过期数据被写进来之后，可能被看到几分钟，也可能几个小时**，取决于它落进的分区上一次 TTL merge 是什么时候。

确认的办法是看数据本身：

```sql
-- 最近写进来的数据里，有多少已经超出了 TTL 窗口
SELECT count(), min(<ttl_column>), max(<ttl_column>)
FROM <table>
WHERE <ttl_column> < now() - INTERVAL 1 MONTH;
```

这个数不为 0、而且过一阵变成 0，就是 TTL 在删。修复不在 ClickHouse 这边，在写入端：过滤掉超出保留期的数据，或者确认这批存量数据本来该不该进这张表。

另外，`MATERIALIZE TTL`（给存量数据补算 TTL）是作为 mutation 在后台池里执行的，和 merge 共用一个池；池里空闲额度低于 `number_of_free_entries_in_pool_to_execute_mutation`（默认 20）时，新的 mutation 不会启动。所以补算 TTL 生效得慢，不一定是没生效。

## 留给读者的

1. **先看结果怎么变，再找原因**：固定几个值来回跳 → 副本不一致；跳但会收敛 → 同步延迟；单调变少 → 去重未完成；先有后无 → TTL
2. **`internal_replication` 不负责同步**，它只决定分布式表写一个副本还是全部副本；同步靠 `ReplicatedMergeTree`
3. **确认副本是否一致，绕开分布式表**，用 `clusterAllReplicas` 逐副本 `count()`
4. **原地转换成 `ReplicatedMergeTree` 之前，先让各副本数据一致** —— 出了这个问题，它们本来就不一致
5. **去重键要被分片键覆盖** —— `FINAL` 不跨分片，merge 不跨分区
