# 百万个只写一次的文件：Fluent Bit 的规模天花板，和另一种采集模型

> 银行一笔交易一个日志文件，证券每天落一批 dbf —— 这类系统的日志是**只写一次**的：写完就是终态，再也不变。一个目录一天两三万个文件，保留一年，就是几百万。
>
> Fluent Bit 不是为这个场景设计的。这篇读它的 `in_tail` 源码，回答三个问题：**它在这个场景下会在哪里撞墙**；**哪些墙是架构决定的、哪些只是还没做**；以及 **另一种采集模型是怎么绕过去的**。
>
> **我的立场**：我们自己做采集器，正是为这个场景做的。所以第五节写我们的模型时，它自己的边界问题和踩过的 bug 也一并写出来。

本文是 Fluent Bit 源码系列的第二篇。上一篇：[先不伤害宿主，再谈不丢数据](/systems/agent/fluent-bit-backpressure-delivery)。源码基线 v5.1.1（`a31cf11a2`），发布前在上游 master `a92d414c1`（2026-10-09）上复核过。

---

## 一、它的模型：长期持有 fd 和 watch

`in_tail` 的低延迟建立在一个前提上：**每个被监控的文件，都长期持有一个 fd 和一个 inotify watch。**

这个设计在它的主战场上是对的。K8s 节点上是几十到几百个持续写入的滚动日志，kubelet 和 logrotate 负责清理历史文件。持有 fd，文件被 rename 甚至 `rm` 之后还能把剩余数据读完 —— **轮转不丢数据的基础就是这个 fd。**

但 fd 和 watch 都是有限资源（`ulimit -n`、`fs.inotify.max_user_watches`）。文件数一上去，它只剩一个降级手段：`ignore_older` + `ignore_active_older_files` —— 文件的 mtime 老过阈值，就关掉 fd、摘掉 watch、移出监控。

**这是 `in_tail` 唯一能主动释放资源的机制。** 下面两个问题都出在它身上。

## 二、淘汰时不看「读完没有」

淘汰的判断在 `check_purge_deleted_file()` 里（`plugins/in_tail/tail_file.c`），只有一个条件：

```c
if (ctx->ignore_older > 0 && ctx->ignore_active_older_files) {
    mtime = flb_tail_stat_mtime(&st);
    if ((ts - ctx->ignore_older) > mtime) {          /* 只看 mtime 老不老 */
        flb_tail_scan_register_aged_out_inode(...);
        flb_tail_scan_register_ignored_file_size(..., flb_tail_file_db_offset(file));
        flb_tail_file_remove(file);                  /* 关 fd、摘 watch、移出监控 */
    }
}
```

**没有检查文件是否已经读完。**

淘汰时保存了 offset，看起来可以续读。但重新捡起来的条件是 **mtime 变新**（`tail_scan_glob.c`）：

```c
if (aged_out_inode == (uint64_t) st.st_ino) {
    mtime = flb_tail_stat_mtime(&st);
    if (mtime > 0 && (now - ctx->ignore_older) > mtime) {
        continue;                   /* mtime 还是老的 → 继续跳过 */
    }
}
```

对只写一次的文件，mtime 永远不会再变：

```
文件写完 → mtime 冻结
  → 文件太多在排队 / 下游背压 / 文件太大，还没读完
  → ignore_older 到期 → 淘汰（offset 存了，但用不上）
  → 之后每一轮扫描：mtime 还是老的 → continue
  → 没读完的部分永久丢失，没有 error，也没有 warn
```

而这两个条件是**天然同时成立**的：文件多，才需要配 `ignore_older` 来救 fd；文件多，读取才会排队、来不及读完。

这段逻辑上游今年改过两次：4 月的 `22f8800ff` 和 6 月的 `0264c0b8c`。后者的提交说明写得很清楚 —— 淘汰时登记 inode 和 offset，**「以便文件的 mtime 之后被新的写入刷新时，可以从保存的位置续读」**。两次修改都在完善「文件睡着了，醒来再接着读」这条路径。它的隐含假设是：**被淘汰的文件还会再被写。** 只写一次的文件不满足这个假设，所以这两次修改都没有覆盖它。

修法是在淘汰条件里补一条「已读完」；退一步，至少在淘汰一个没读完的文件时打一条 warn。

## 三、淘汰记录本身无界增长

淘汰机制依赖两张 hash 表：一张记被淘汰的 inode，一张记淘汰时的 offset。它们是这样创建的（`plugins/in_tail/tail_config.c`）：

```c
ctx->ignored_file_sizes   = flb_hash_table_create(FLB_HASH_TABLE_EVICT_NONE, 1000, 0);
ctx->aged_out_file_inodes = flb_hash_table_create(FLB_HASH_TABLE_EVICT_NONE, 1000, 0);
                                                  /* 永不淘汰          1000 个桶  不限容量 */
```

`EVICT_NONE` 是永不淘汰，最后一个参数 `0` 是不限容量，**1000 是桶数不是容量**。key 是完整的文件路径字符串。

以 100 万个文件为例：

| 维度 | 影响 |
|---|---|
| 内存 | 每个被淘汰的文件在两张表里各留一条，永不释放 |
| 查找 | 100 万条 ÷ 1000 个桶，平均链长 1000，查找退化成线性扫描 |
| CPU | 每轮 glob 扫描对每个文件查一次表 —— 每轮 100 万 × 1000 次比较 |

**唯一能救 fd 的机制，在它的目标场景（文件很多）下，先把内存和 CPU 拖垮了。** 而且没有指标、没有日志，只表现为内存缓慢上涨。

修法不难：表本来就是缓存语义，换成带上限的淘汰策略（`EVICT_OLDER`），代价最多是某个文件被重新打开一次；或者按扫描周期清掉已经不匹配 glob 的条目；再把表的大小暴露成指标。

## 四、补得了的，和补不了的

把 Fluent Bit 放到百万文件的场景里，问题可以分成三类。

### 补不了：长期持有 fd（架构取舍）

要「读完就关」，就得放弃对 inode 的引用 —— 文件被 `rm` 之后剩下的数据就读不到了，**轮转不丢数据的基础没了**。watch 也一样，百万个 watch 本身就撑不住。

想读完即关，只能退回轮询，延迟从毫秒级变成扫描周期级。**这是真正的鱼与熊掌，没有对错。**

### 补得了：fd 没有上限（实现缺失）

`in_tail` 对打开文件数不设上限，撞到 `ulimit -n` 为止，撞墙后也没有专门的 `EMFILE` 提示。这不是架构决定的，在现有模型里就能补：

1. **准入上限 + 等待队列**：超过上限的文件先排队，不打开
2. **LRU 淘汰**：现成的 `flb_tail_file_remove()` 会关 fd、摘 watch、保留 offset，拿来淘汰最久不活跃的文件
3. **失败退避**：打不开的文件一段时间内不再重试，而不是每轮扫描重复报错

代价是被淘汰的文件延迟变高 —— 但这正是资源受限时该做的降级：**宁可部分文件延迟高，也不要 fd 耗尽让整条管道停摆**（上一篇第四节）。

上游已经在做前两条：在途的 PR [#12441](https://github.com/fluent/fluent-bit/pull/12441) 给所有 tail input 加了一个进程级共享的 `max_open_files` 预算，用到 75% 时告警，并回收休眠文件的 fd，被延后的文件保留 offset。起因之一是 [#12432](https://github.com/fluent/fluent-bit/issues/12432)：一个 Windows 用户每天产生 5000～10000 个审计日志，文件数过了约 8200 就开始报 `Too many open files`，而其中大部分是早已读完、只为审计保留在盘上的历史文件。写作时这个 PR 还没有合入。

### 介于两者之间：目录级短路

`in_tail` 用 POSIX `glob()` 展开路径，把整个展开过程交给了 libc —— **也就失去了在展开过程中插入判断的机会**。一个早已全部过期的历史目录，每一轮都会被完整展开一遍。要在目录这一层短路，得重写扫描层。工作量大，但不是架构冲突。

## 五、另一种模型：无状态轮询 + 有界的 fd 池

我们自己的采集器面向的正是这个场景，走的是另一条路：**不长期持有 fd，用轮询发现变化，fd 放在一个有上限的池子里。** 池子满了，新的候选文件先登记、不打开；下一轮扫描发现某个文件比上次读到的位置更大，再打开、seek 到上次的位置续读。打不开的文件进入退避期，一段时间内不再重试。

代价是延迟：变化要等下一轮扫描才被发现，不是毫秒级。对只写一次的文件，这个代价几乎不存在 —— 文件出现的那一刻，它的内容就已经写完了。

这套思路的核心是「文件过期」：**对已经采完、确定不会再变的文件做标记，停止监控**，把「监控全量」降成「监控活跃量」。我作为第一发明人把它申请了发明专利 ——《一种针对海量小文件数据采集技术优化方法》（[CN120541047A](https://patents.google.com/patent/CN120541047A/zh)，2025-05 申请，2025-08 公开）。专利文本里记录的效果是在不影响采集性能的前提下，CPU 和内存使用率下降 70% 以上。

在这个模型上，资源控制分三层，越靠前越省：

| 层 | 作用时机 | 省掉了什么 |
|---|---|---|
| **路径日期模板** | 展开路径**之前** | 路径里按日期分目录的，只展开「昨天到今天」两个目录。历史目录从来不进候选集，一次 `opendir` 都不做 |
| **目录过期** | 扫过一次之后 | 一个目录下所有文件都过期、目录本身也很久没变，就整个记下来，之后连 `opendir` 都不做 |
| **文件过期** | 文件读完之后 | 释放 fd，不再参与扫描 |

「昨天到今天」这个范围是必需的：零点刚过的时候，昨天的目录里可能还有刚写完、没采完的文件，只取今天会漏。

### 文件过期：三个条件同时满足

和第二节的 `ignore_older` 对比，关键在第二个条件：

```
文件过期 ⇔  自上次处理之后 mtime 没变
         且 已经读到了文件末尾          ← ignore_older 缺的正是这一条
         且 mtime 距今超过过期阈值
```

| 维度 | 我们的模型 | Fluent Bit `ignore_older` |
|---|---|---|
| 判定条件 | 三条件合取，含「已读完」 | 只看 mtime |
| 过期状态 | 持久化到磁盘，重启不重扫 | 纯内存，重启即丢 —— 百万文件时重启就是一场资源风暴 |
| 检查频率 | 独立定时器，默认一小时 | 每轮清理 + 每次 glob 扫描都查，放大第三节的线性查找 |
| 可观测 | 有过期文件数的指标 | 没有 |

### 目录过期：一票否决

目录过期是合取式的：进入目录前先乐观假设它已过期，里面**任何一个**文件没过期、**任何一个**子目录没过期，都会一票否决；子项全部过期之后，还要再看目录自身的 mtime —— 目录刚有过增删条目，也不算过期。

只有这样判定，才敢在扫描入口直接跳过整个目录。一年 365 个日期目录、每个两三万文件，历史目录就是直接放过，而不是逐个文件判断。

### 它自己的边界问题

公平起见，我们的模型也有自己的问题。

- **过期标记用文件路径作 key，不是 `设备号:inode`。** 同一路径的文件被删掉重建（inode 变了），会命中旧的过期标记被误跳过。Fluent Bit 反而处理了这一点：它在扫描时比对 inode，不一致就清掉旧记录。对「文件名唯一、不复用」的场景（只写一次的文件基本如此）没有影响，但它是一个真实的边界。
- **持久化的过期标记同样有膨胀风险** —— 百万个条目落盘，和第三节是同一类问题，是否有回收我们还没有验证。
- **路径日期模板写错不报错。** 写成字面量 `YYYYMMDD` 而不是 `%Y%m%d`，路径合法、只是匹配不到任何文件，静默采集为零。应该在配置校验时拦下来。

还有三个已经修掉的 bug，值得一提的是它们都出在**防止资源耗尽**的功能里：日期偏移解析的缓冲区少留了一个终止符，偏移写满时越界读栈；目录打开失败的错误处理把入参当输出缓冲区，递归时覆写了上层的栈变量；同一处错误路径提前返回，跳过了关闭目录 —— **在防 fd 耗尽的功能里泄漏 fd。**

## 六、为什么上游没做这些

答案不是「没碰到过大规模」。代码里留着他们撞过墙的痕迹（`plugins/in_tail/tail_db.c`）：

```c
/*
 * The legacy implementation builds:
 *   DELETE ... WHERE inode NOT IN (?,?,?,...);
 * which requires one bound parameter per inode and fails when the number of
 * monitored files exceeds SQLITE_LIMIT_VARIABLE_NUMBER (commonly 32766 ...).
 */
```

**有人真的跑到了 32766 个以上的文件，修复是用户报告推动的。** inotify `ENOSPC` 的专门提示、`ignore_older` 这个功能本身，都是同类痕迹。

所以准确的说法是：**碰到过几万，没碰到过百万。**

| 量级 | fd | watch | 有效的解法 |
|---|---|---|---|
| 几万 | `ulimit -n 65536` 撑得住 | `max_user_watches=524288` 撑得住 | **调内核参数** |
| 百万 | 调参数也不可能 | 同样不可能 | 必须换模型 |

在几万的量级上，「调 sysctl」是有效的答案，社区自然没有动力去做资源池、LRU 和目录短路。**这是合理的工程判断，不是疏忽。** 场景形态也解释了这一点：只写一次的海量小文件是金融、证券这类传统行业的形态，这些系统很少用 Fluent Bit，社区里既没有需求推动，也没有人贡献。

[#12441](https://github.com/fluent/fluent-bit/pull/12441) 的出现说明，这个天花板正在被一些用户碰到。

## 留给读者的

1. **`ignore_older` 只看 mtime，不看读完没有** —— 只写一次的文件被淘汰后不会再被捡起来，没读完的部分静默丢失
2. **淘汰记录表永不淘汰、只有 1000 个桶** —— 百万文件时，救 fd 的机制先拖垮了内存和 CPU
3. **长期持有 fd 是架构取舍，fd 没有上限是实现缺失** —— 前者换不了，后者上游正在补
4. **只写一次的文件，轮询 + 有界 fd 池几乎没有代价** —— 文件出现时内容已经写完，毫秒级延迟没有意义；关键是「文件过期」：把监控全量降成监控活跃量
5. **资源控制越靠前越省**：展开路径之前裁剪 > 目录级短路 > 文件级过期
6. **Fluent Bit 在几万文件内够用，到了百万没必要硬上** —— 它的优势在生态、多信号和处理管道，不在海量小文件
