# 一个会让指标悄悄断流的设计，和我们改了三次的 schema

> 指标写进 ClickHouse，最自然的做法是拍平成一张大宽表。这条路我们走过，然后改了三次。
>
> 中间踩到的那个坑特别值得说：**用户在业务系统里改了一个标签，指标数据在时间上就断了** —— 不报错、不丢数据，就是查不出连续的曲线。

## 一、起点：为什么不能只用一张宽表

指标数据有三个特征：

- **指标数量极多，指标名不固定** —— 不适合 schema 固定的表
- 用 JSON 或 Map 存，读写性能没法保证，也不利于管理
- **列存天然适合把它拍平成大宽表** —— 这是对的方向

sinker 的动态表 schema 特性（`dynamicSchema`）正是为此：根据 Kafka JSON 里的字段自动扩展表的列名，上限由 `maxDims` 控制，配白名单黑名单防脏数据。

方向对了，但一张表装不下。

**每一个指标都是一条时间序列。** 如果全存进一张大宽表，这张表会非常庞大 —— **行数多、列数也多**，插入和查询性能都不会好。

## 二、第一次改：拆成两张表

把「随时间变化的值」和「不随时间变化的维度」分开。

**`metric` 表** —— 只有三个字段，极窄极长：

| 字段 | 说明 |
|---|---|
| `__series_id` | 指标序列 ID，标识这是哪一条序列 |
| `timestamp` | 时间 |
| `value` | 值 |

**`metric_series` 表** —— 宽表，存维度：

| `__series_id` | `__name__` | `label` | metric1 | metric2 | … | metricN |
|---|---|---|---|---|---|---|
| 按指标属性维度算出的序列 ID | 指标名 | 指标携带的标签 | | | | |

查询时两张表按 `__series_id` 关联。

好处很直接：`metric` 表一行只有三列，写入量再大也是窄行；维度信息在 `metric_series` 里，**同一条序列只需要存一份**，不随每个数据点重复。

（sinker 里这对应 `prometheusSchema: true`，会把一条记录自动拆成两张表，series 表名默认是 `tableName` 加 `_series` 后缀。）

## 三、然后撞上了那个坑

`__series_id` 是**根据指标的属性维度计算出来的** —— 也就是说，**标签参与了它的计算**。

问题出在这里。

用 exporter 暴露指标的时候，很可能携带一些**与指标本身无关的 label**。比如同样都是 CPU 使用率，可能一部分是业务 A 机器的数据，另一部分是业务 B 机器的。这类业务标签会被一起带进来。

于是两件事同时发生：

**① series 表膨胀**

查询的人可能只关心业务 A 的指标。但如果这些业务标签参与了 `__series_id` 的计算，就会产生**超级多的 `__series_id`**，整个 series 表膨胀得特别厉害，时间久了还会堆出大量无用的垃圾数据。

**② 指标断流 —— 这个更要命**

::: danger
**业务标签一变（而变动业务标签是经常会发生的事），`__series_id` 就变。**

`__series_id` 一变，这条序列在 `metric` 表里就换了个身份 ——
**同一个指标的数据在时间上不再连续，甚至直接断流。**
:::

注意这个故障的形状：

- 不报错
- 不丢数据（新 series 的数据照样在写）
- 只是你在 Grafana 上看到曲线断了一截，或者干脆换了一条新线

**而触发它的动作，是某个人在业务系统里改了一个标签** —— 那个人完全不知道自己动了监控。

## 四、第二次改：引入 `__mgmt_id`

根子在于**把两类不同性质的信息混在了一个 ID 里**：

- 指标本身的身份（它是什么指标、哪台机器、哪个实例）
- 业务管理属性（它属于哪个业务、哪个团队、哪个项目）

第一类稳定，第二类经常变。**混在一起算 hash，就等于让经常变的东西去决定稳定的东西的身份。**

所以引入了 `__mgmt_id`，**它代表管理标签的 id**，把具体的指标 id 和业务 id 分开：

```
__series_id   ← 只由指标自身属性决定    → 稳定
__mgmt_id     ← 由业务管理标签决定      → 可变
```

这样保证了**指标的纯粹性**：不会因为改了某个业务标签，导致指标无法被查询到。series 表的量级也更加可控，不会无限制膨胀。

## 五、第三次改：`bmSeriesMap` 和它的内存问题

分开之后带来了新问题。

业务管理标签在同一业务上是一致的，但可能涉及多个指标；同一个指标也可能因为业务标签改变产生多个 `__mgmt_id`。**两者是多对多关系。**

而对于**相同的 `__mgmt_id` 和 `__series_id` 的组合，我们不希望每次都插入** —— 那会带来非常大的性能开销（插入更多数据，merge 和 final 查询都会变慢）。

期望的行为是：**只有当 `__series_id` 和 `__mgmt_id` 之间的映射关系发生改变时，才 insert 新记录。**

那就需要一个 map 记录这两者的映射关系。

**然后这个 map 自己成了问题：**

- 随着指标数量增多、业务标签不断扩展，这种映射关系**可能达到数百万级**
- 这么大的数据量存在内存里，有严重的内存爆炸风险
- 每次插入都去数据库实时查询？性能更差
- 而且**某些任务可能早就不用了，但映射关系还留在内存里** —— 纯粹的垃圾数据，需要清理机制

解法是 `bmSeriesMap` 的 reload 机制：

```
只保留「一天以内的有效指标」            → 控制总量
每隔一个小时从数据库实时查询最新映射     → 保证准确
   并刷新到 map 中
```

对应两个配置项：

| 配置 | 默认值 | 含义 |
|---|---|---|
| `activeSeriesRange` | `86400`（1 天） | 有效 series 的时间范围 |
| `reloadSeriesMapInterval` | `3600`（1 小时） | 自动重新加载 seriesmap 的时间间隔 |

**这两个数不是拍出来的，是「内存占用」和「映射准确性」之间的一组取舍** —— 范围放大，内存涨；reload 变稀，新序列被识别得更晚。

## 六、顺带一个相关设计：`recordPoolSize`

同一类问题：**内存不是配出来的，是流控出来的。**

sinker 写 ClickHouse 这一步是**异步**的 —— 起一个协程专门写入，主流程不等结果，立刻处理下一批 fetch。本意是尽可能提高写入性能：只要写入不报错，就让它慢慢写，写完了再提交 offset。

但这带来一个风险：

> 如果 ClickHouse 本身因为硬件资源原因导致写入效率不高，而 Kafka 的 lag 又积压特别多，
> 很可能 fetch 了很多数据，都阻在 flush 这一步。
> **而 sinker 在数据未完全写入成功之前，是不会释放这部分内存的。**

表现出来的曲线很有辨识度：

```
sinker 刚启动      →  内存有明显冲高（lag 大，fetch 快，flush 慢）
lag 慢慢追上       →  内存缓缓降下来
```

`recordPoolSize` 是每个进程实例最多可以处理的消息上限。池子里积压的消息达到上限，就**暂缓从 Kafka 拉取新消息**，直到池子有空闲空间释放出来。

**这就是一个反压机制。** 它解决内存占用过高的问题，**代价是写入速度会有一定降低** —— 建议设成 `bufferSize` 的 3～4 倍。

## 尾声：三次修改的共同形状

::: tip
回头看，这三次改的都是同一类问题：**某个量在设计时被默认为「不会太大 / 不会经常变」，然后它变了。**

- 一张宽表 → 默认了指标数量可控，结果行列都爆
- `__series_id` 含业务标签 → 默认了标签稳定，结果它经常变
- `bmSeriesMap` 全量常驻 → 默认了映射关系数量有限，结果到了百万级

**每一次的解法都不是「换个更强的实现」，是「把那个会变的东西拆出去，单独给它一套生命周期」。**

拆成两张表、拆出 `__mgmt_id`、给 map 加 `activeSeriesRange` —— 都是同一个动作。
:::

而第三节那个坑值得单独记住：

> **一个不在监控系统里的人，改了一个不在监控系统里的字段，
> 让监控断流了。而监控本身没有报任何错。**

这类跨系统的隐式耦合，是可观测性产品里最难被测出来的一类缺陷 —— 因为**每一个单独的系统都在正常工作**。
