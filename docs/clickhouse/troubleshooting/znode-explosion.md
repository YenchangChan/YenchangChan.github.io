# znode 爆炸与线程池

<!-- 骨架按事故的真实顺序走，不要按"分析-定位-解决"的模板走。

## 起点：一次救火动作引爆了集群
  16 节点 8 分片、400 张表、日增 20TB。
  ZK 早就扛不住 → 客户决定扩容 → 扩容要重启 → 会话中断、大量表只读、znode 冲到 2700 万。
  硬约束：Kafka 只保留 3 天。

## 我远程给的两个建议，一对一错
  对的：掐断上游写入，让 merge 追平。
  错的：对 parts 多的表跑 OPTIMIZE TABLE —— 把优化目标搞反了，
        too many parts 判定的是数量，OPTIMIZE 优化的是数据组织，
        它会挑最大的 part 合并，长任务占满线程池，小 part 反而排不上队。
  第三重：客户等不及恢复了写入。数据保住了，现场更糟了。

## 到现场：把诊断降一维
  客户在加强 ZK，我去掐 ZK 的负载来源。
  background_pool_size 16 → 64（128c 机器，余量够）。
  2700 万 → 700 万。

## 四五个月后：回升到 1600 万
  这次不是 merge，是副本同步队列。
  system.replication_queue 的 reason 字段：fetch 线程数已达上限 8，几千万条全是这一条。
  说明第一次只把瓶颈从 merge 挪到了 fetch。

## 改了不生效
  决策依据先说：线程池满、但 CPU 很闲 —— 并发度问题，不是资源问题。
  调 background_fetches_pool_size，没反应。
  关键转折：先别问"为什么不生效"，先问"它到底生效了没有"。
  查 settings（散在三张表里，当时不确定哪张，都查了）→ 确认没生效
  → 翻 changelog、读源码 → 22.5 起该参数从 profile 级升为全局配置。
  改对位置，300 万。
