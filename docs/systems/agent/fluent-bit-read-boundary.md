# Fluent Bit 源码笔记（四）：GBK 日志丢了 27.4%，读取边界上的数据丢失

> 给 `in_tail` 配上 `generic.encoding=GBK` 采一份 GBK 日志，2000 行收到 1452 行，**丢了 27.4%**。丢失的位置精确落在 32KB 的读取边界上，整段整段地消失；全程只有一条和数据丢失毫不相干的 error。
>
> 同一个根因在 UTF-16 上表现成每个边界丢一行，在 `.gz` 上表现成「读到一半重启，剩下的永远读不出来」。三者是同一族问题：**文件里的物理位置，和数据流里的逻辑位置，被当成了一回事。**
>
> 这一篇也是我判断错得最多的一篇。三个问题，读源码时的预测都被实测推翻过 —— 有的比预想严重，有的比预想轻。这些推翻的过程我保留在文中。

## 一、两种位置

采集一个文件，要同时维护两种位置：

- **物理位置**：读到了文件的第几个字节。重启后靠它 `lseek` 回去。
- **逻辑位置**：已经处理完的数据，在数据流里到哪了 —— 处理到最后一个完整的行、最后一个完整的字符。

不转码、不解压的时候，两者是一回事，只有一个细节要处理：每次 `read()` 的末尾几乎不可能刚好落在行尾，**最后那半行要留在缓冲区里，等下一次读到后半截再拼起来。** `in_tail` 的普通路径就是这么做的 —— 只把完整的行算作「已消费」，半行留着。

一旦中间加了一层转换（编码转换、解压缩），物理位置和逻辑位置就分开了。这时候必须由转换层告诉调用方「我实际消费了多少源字节」，调用方才知道该把多少字节留在缓冲区里。

**下面三个问题，都是这一步没有做对。**

## 二、GBK：成块丢失，27.4%

### 机制

`in_tail` 有两条转码路径，GBK、GB18030、ShiftJIS、UHC、Big5 走的是 `generic.encoding` 这一条。

**第一步：读取按字节切。** 每次最多读 `buf_max_size`（默认 32KB），边界可能落在一个汉字的两个字节之间。

**第二步：转换遇到残缺字符就停，但报的是成功。** `src/unicode/flb_conv.c` 的转换循环：

```c
l = flb_encoding_verifymbchar(encoding, (const char *)p_iso, len);
if (l < 0) {
    break;                       /* 尾部字符不完整 → 跳出 */
}
...
return p_utf - start_utf;        /* 返回已写出的长度，是正数 */
```

上层只在返回值 `<= 0` 时当作失败，所以这里走的是成功分支。**转换实际消费了多少源字节（`p_iso - iso`），算出来了，但没有往上传。**

**第三步：offset 按全部原始字节推进。** `plugins/in_tail/tail_file.c`：

```c
original_len = end - data;        /* 缓冲区里全部的原始字节 */
...
if (lines > 0) {
    ...
    else if (original_len > 0) {
        *bytes = original_len;    /* 转码路径：按全部原始字节算「已消费」 */
    }
    else {
        *bytes = processed_bytes; /* 普通路径：只算完整的行 —— 这是对的 */
    }
}
```

普通路径用的是 `processed_bytes`，只累加找到了 `\n` 的完整行；转码路径用的是 `original_len`，**把末尾那半行、半个字符，也一起算成了「已消费」**。转换结果随后被 `free` 掉，原始缓冲按这个长度被清掉 —— 末尾那部分两边都没留下。

还有一个旁证：`struct flb_tail_file` 里有一个 `parsed` 字段，名字和赋值时机都像是为「记录没解析完的尾部」设计的，但全项目**没有任何地方读取它**。像是重构时丢掉了消费端。

### 我最初的判断，和实测

读源码时，我的结论是「每次跨边界最多丢一个字符，offset 不会错乱，影响有界」。我甚至估算了丢失量：32KB 缓冲 + 纯中文，平均每 64KB 丢一个字。

**这个结论是错的。** 实测的设计：

- 每行是 `LINE%06d ` 加 24 个汉字，GBK 编码后**每行恰好 60 字节**，2000 行共 120000 字节
- 定长行让三个 32KB 边界的落点可以提前算出来：

| 边界 | 字节偏移 | 落在 |
|---|---|---|
| 1 | 32768 | 第 547 行第 8 字节（ASCII 编号区） |
| 2 | 65536 | 第 1093 行第 16 字节（汉字中间） |
| 3 | 98304 | 第 1639 行第 24 字节（汉字中间） |

| 组 | 配置 | 收到 | 判定 |
|---|---|---|---|
| 对照组 | UTF-8 文件，不配编码 | **2000 / 2000** | 基线完整 |
| 实验组 | GBK + `generic.encoding=GBK` | **1452 / 2000** | 丢 548 行（27.4%） |
| 重复 | 同上，再跑一次 | **1452 / 2000** | 完全可重复 |
| 反证组 | 同上 + `buffer_chunk_size=131072`（大于整个文件） | **2000 / 2000** | 零丢失 → 根因锁定在读取边界 |

收到的最大行号是 2000，排除了「超时没读完」这个解释。

丢失位置精确落在边界上。把 chunk 换成 16KB 再测，缺失区间的起点字节除以 chunk 大小，**全部是整数**：

| chunk | 缺失行 | 行数 | 起点 ÷ chunk |
|---|---|---|---|
| 32KB | 547 | 1 | **1.00** |
| 32KB | 1093..1639 | **547** | **2.00** |
| 16KB | 274、547、820 | 各 1 | **1.00、2.00、3.00** |
| 16KB | 1093..1366 | **274** | **4.00** |
| 16KB | 1639..1912 | **274** | **6.00** |

而且丢失的行数，恰好等于一个 chunk 能装下的行数（32768 / 60 ≈ 546，16384 / 60 ≈ 273）。

### 两种丢法

| 边界落在哪 | 发生了什么 | 丢多少 | 日志 |
|---|---|---|---|
| **ASCII 区** | 循环正常跑完，最后半行没有 `\n`，被 `original_len` 一起算作已消费 | **被切断的那 1 行** | 完全没有 |
| **汉字中间** | 前半个字节被跳过 → 下一个 chunk 从字符的后半截开始解码 → **整块错位** → 换行符 `0x0A` 被吞进一个双字节字符里 → 整块切不出一行 | **整个 chunk** | 1 条 error |

那条 error 长这样，字节序列正好是**半个汉字 + 换行符**：

```
[error] [wchar] character with byte sequence 0xdd 0x0a in encoding code "13"
        has no equivalent in encoding code "1"
```

**548 行的丢失，全程只有这一条 error，内容只字未提数据丢失，更没有数量。** 运维侧既无法从日志判断损失规模，也没有指标可看。

错位只持续一个 chunk：offset 始终按 `original_len` 推进，每个 chunk 的起点固定在 chunk 大小的整数倍上，下一轮自动重新对齐。所以 32KB 那组丢完 1093..1639 之后，1640 起全部正常。

另外，对收到的 1452 行逐行数汉字，**全部是 24 个，没有一行缺字**。所以「每 64KB 丢一个字」也不成立 —— 实际是要么整行完好，要么整块消失，没有中间态。

### 为什么一直没人发现

这个问题严重到会让 `generic.encoding` 在 GBK 日志上基本不可用，按理早该有人报告。读源码时我怀疑自己漏看了某处补偿逻辑；实测的结论是没有漏看 —— 更可能的解释是这个功能用的人还不多（`generic.encoding` 是较新的功能），问题还没有暴露。截至发布，上游没有查到相关报告。

## 三、UTF-16：比预想的轻，但同一个根因

Windows 上 SQL Server 的日志是 UTF-16LE，走另一条转码路径 `unicode.encoding`（simdutf）。

### 我最初的判断

读源码时，我预测这条路径比 GBK 严重得多，理由是一条三步的链：

1. 缓冲区为字符串终止符留了 1 字节，空缓冲时读取量恰好是**奇数**（32767），UTF-16 是 2 字节定长，奇数长度必然切在码元中间
2. simdutf 的封装层遇到奇数长度，**直接丢掉最后一个字节**，仍然返回成功
3. offset 按全部字节推进 → 下一轮从奇数位置开始读 → **后续所有码元永久错位**，`\n` 的 `0A 00` 变成 `00 0A`，找不到行尾，撞上 `Buffer_Max_Size`，整个文件停止采集

UTF-16 没有自同步性，一旦错位就恢复不了。我当时的结论是：「SQL Server 的日志，大概率在第一次跨 32KB 边界时整个文件停止采集。」

### 实测：三个预测一个都没出现

每行 72 字节（UTF-16LE），2000 行，跨 4 个 32KB 边界：

| 组 | 收到 | |
|---|---|---|
| 对照组（UTF-8） | **2000 / 2000** | |
| UTF-16LE + `unicode.encoding=utf-16le` | **1996 / 2000** | 丢 4 行（0.2%） |

没有乱码，没有停采，读到了最后一行，**没有任何 error**。启动日志给出了原因：

```
[ info] [input:tail:tail.0] adjusted buf_max_size to 32769
[ info] [input:tail:tail.0] adjusted buf_chunk_size to 32769
```

配了 `unicode.encoding` 时，`adjust_buffer_for_2bytes_alignments()` 会把缓冲调成 32769，于是读取量是 32768 —— **偶数，码元根本不会被切破**。我的链条第一步就不成立，是读源码时漏看了这个函数。

真实存在的只有一件事：丢失的 4 行 `[456, 911, 1366, 1821]`，**每一行都恰好骑在 32768 的整数倍上**。被边界切断的那一行，前半截没有 `\n` 不成行，后半截因为 offset 已经按 `original_len` 推过去了，永远读不到 —— 和 GBK「边界落在 ASCII 区」那种丢法完全一样。

| | GBK | UTF-16LE |
|---|---|---|
| 缓冲对齐保护 | 没有（变长编码，固定对齐解决不了） | 有 |
| 边界切破字符 | 会 → 下一块整块错位 | 不会 |
| 实测丢失 | **27.4%**（边界行 + 整块） | **0.2%**（仅边界行） |
| 日志 | 1 条失真的 error | 没有 |

**结论和我最初的判断正好反过来：UTF-16 比 GBK 轻得多。** 有对齐保护的那条路径只剩一个共性问题，没有保护的那条才是真正高危的。

## 四、一个修法，修两处

根因相同：**转换实际消费的源字节数，没有回传给调用方。** 两处的信息都是现成的：

```c
/* simdutf 封装层：截掉奇数字节后的 len 就是实际消费量 */
/* generic 转换层：p_iso - iso 就是实际消费量 */
int flb_conv_convert_to_utf8(..., size_t *consumed);

/* tail_file.c：按实际消费推进，而不是按读进来的全部字节 */
*bytes = consumed;
```

残缺的字节会留在缓冲区里，等下一轮读到后半截拼上 —— **这正是普通路径本来就有的行为**，没有任何算法变更。

我在本地按这个思路改了 `tail_file.c`（+32 −2），双向验证：GBK 组 **2000 / 2000**，UTF-8 回归组 **2000 / 2000**。

这个修法依赖一个前提：`generic.encoding` 覆盖的编码都是 **ASCII 安全**的 —— 多字节序列里不会出现 `0x0A`。GBK、Big5、ShiftJIS、UHC、GB18030 按字节范围定义都满足这一点，但**我只实测了 GBK**，其余四种还没有各造一个样本验证。

## 五、gzip：读到一半重启，剩下的永远读不出来

`in_tail` 按文件名后缀自动识别 `.gz`，边读边解压，没有配置开关。这里的「两种位置」最明显：压缩文件的物理字节位置，和解压后的数据位置，是两个完全不同的数。

`struct flb_tail_file` 里其实两个都有：`offset` 是物理位置，`stream_offset` 是解压后的逻辑位置，注释里写明了后者可能比文件还大。但持久化时（`plugins/in_tail/tail_file.h` 的 `flb_tail_file_db_offset()`），压缩文件走的是一个单独的分支：

```c
if (file->decompression_context != NULL) {
    return file->offset;          /* 压缩文件：直接存物理位置 */
}
```

重启后，`lseek` 到压缩流的中间，交给一个全新的解压上下文 —— gzip 是流式压缩，缺了前面的字典状态，这里读到的字节连 gzip 的魔数都不是。

### 实测：比预想的严重

读源码时我的判断是「`.gz` 是只写一次的，读完了就不会再触发，实际影响有限」。实测用的是一个 71 MB 的 gzip（150 万行），读到一半时 SIGTERM 正常关闭：

| 组 | 场景 | 结果 |
|---|---|---|
| 实验组 | 读到 50% 中断 → 重启 | **0 行**，`[gzip] invalid magic bytes` |
| 再重启一次 | | **0 行**，同样的错误 |
| 反证组 | 删掉 DB，从头读 | **1500000 / 1500000**，文件本身完好 |
| 对照组 | 非压缩文件读到 21% 中断 → 重启 | 314336 + 1185664 = **1500000**，零丢失零重复 |

最严重的是第二行：解压失败，没有任何数据被消费，**offset 一个字节都没动**。于是每一次重启都重放同一个失败，永远卡在 50%。750565 行永久丢失，不存在任何自愈路径；唯一的人工恢复手段是删掉这条 DB 记录，代价是整个文件从头重采。

这条至少有明确的 error 日志 —— 比前两个强。

### 我的修法不如上游

我的本地修法很直接：压缩文件重启时退回 0，从头解压。实测结果是丢失变成了 0，但**重复了 694822 行（46.3%）** —— 我只是把「最多一次」换成了「至少一次」。

写 issue 之前查重，发现上游已经有一个在途的 PR [#11269](https://github.com/fluent/fluent-bit/pull/11269)（关联 [#11265](https://github.com/fluent/fluent-bit/issues/11265)）。它在 DB 里新增了两列：

- `anchor`：一个合法的 gzip member 边界的物理位置，可以从这里开始解压
- `skip`：在这个 member 里已经消费掉的**解压后**字节数

重启时 `lseek` 到 `anchor`，解压后丢弃前 `skip` 个字节，从断点精确续读。

我把 PR 分支拉下来编译，用同一个 71 MB 的文件实测：

| | 上游 master | 我的本地修法 | PR #11269 |
|---|---|---|---|
| 丢失 | 750565 行（50%） | 0 | **0** |
| 重复 | —— | 694822 行（46.3%） | **0** |
| 语义 | 数据丢失 | 至少一次 | **恰好一次** |

第一轮读到第 684252 行，重启后从第 684253 行接上，精确衔接；已经读完的文件再重启，读 0 行，不重复采集。数字也对得上：`skip = 63635436` = 684252 行 × 93 字节。

**两个维度描述进度（从哪里开始解压 + 解压后跳过多少），才能做到恰好一次。** 我的修法只有一个维度，所以只能在丢失和重复之间二选一。

这件事的另一个教训是：**提修复之前先查上游。** 如果我直接提交，不仅是重复劳动，还会把一个更差的方案推给维护者。写作时这个 PR 仍未合入。

## 六、两个小瑕疵

**截断不看字符边界。** 多行合并超长时的截断（`src/multiline/flb_ml_group.c`）和单行 `truncate_long_lines` 都是纯字节截断，可能砍在汉字中间。但输出端兜住了：JSON 输出会校验 UTF-8，非法字节走 `\uXXXX` 转义，下游解析不会失败。例外是不转义直写的路径（`flb_utils_write_str_raw()`）—— 用 raw / msgpack 格式输出时，非法字节会原样传到下游。

**一段处理 `\r` 的死代码。** 切行时：

```c
if (len >= 2) {
    crlf = (data[len-1] == '\r');
    if (len == 1 && crlf) {       /* 外层已经保证 len >= 2，这里永远进不来 */
        ...
    }
}
```

主逻辑是对的，Windows 的 CRLF 日志不会在行尾残留 `\r`。只有配了 `Skip_Empty_Lines Off` 时，只含一个 `\r` 的行会把 `\r` 当成内容采上来。不涉及数据丢失。

## 留给读者的

1. **配了 `generic.encoding` 的 GBK 日志，在修复之前不要用默认的读取缓冲** —— 边界切在汉字中间时，整个 chunk 消失；临时规避是把 `buffer_chunk_size` 调大，但这只能降低频率
2. **物理位置和逻辑位置一旦分开，转换层必须回传「实际消费了多少」** —— 三个问题都是这一步没做
3. **UTF-16 比 GBK 轻得多**：有缓冲对齐保护的路径只剩边界丢行，没有保护的路径才是高危的
4. **压缩文件的续读进度要两个维度**：从哪里开始解压 + 解压后跳过多少。只有一个维度，就只能在丢失和重复之间二选一
5. **读源码得出的严重性判断，必须实测** —— 这一篇里三个问题的预测，一个比实际轻得多，一个比实际重得多，一个方向对了但程度错了
6. **提修复前先查上游在途的 PR**
