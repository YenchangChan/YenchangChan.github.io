# 采集器被两家客户判了死刑，然后我们翻了案

> 两家金融客户，服务器 hang 死。两边的内核团队独立分析，给出了同一个结论：**我们的采集器干的。**
>
> 这篇记录怎么把这个结论推翻 —— 根因是 RedHat 在 `3.10.0-862.el7` 移植补丁时抹掉了一个 `__GFP_NOFAIL` 标志，让 jbd 事务与 memory cgroup OOM 互相锁死。采集器只是那个把触发条件凑齐的人。
>
> 客户名称、进程名与业务信息均已脱敏；**内核函数名、锁名、标志位一律保留原样** —— 这篇的价值就在这些符号上。

## 一、指控

客户 A 的 Redis 服务突然不可访问，大面积业务受影响。排查发现两台部署 Redis 的服务器都 hang 死了。

客户的技术专家分析后指出：hang 死的时间点上，**我们的采集器进程 CPU 占用高达 300%，并且多次 OOM**。结论是采集器频繁 OOM 导致了机器 hang 死。

内部同步信息时发现，客户 B 那边半年内已经陆续出现 5 次同样的现象。客户 B 的内核专家做了更深入的分析，结论一致：**采集器引发的服务器 hang 死**。

两家客户，独立分析，同一个结论。

## 二、对方的证据链是扎实的

必须承认，客户 B 给出的分析质量很高。

`atop` 上的内存曲线：

```
11:53:22    free: 507.4M     cache: 9.4G
11:53:32    free: 9.9G       cache: 726.0M
```

十秒内 free 从 507M 涨到 9.9G，file cache 同步释放 —— 而且几乎没有 dirty page，说明回收的是 clean page，是一次直接回收。

**就在这次回收的时刻，采集子进程 D 住了。**

`vmcore` 显示该进程正处在收到信号的过程中，随后调用 `__getblk()` 等待可用内存；拿不到，于是反复调用 `free_more_memory()` 触发回收流程，卡死在 `shrink_inactive_list`。

`dmesg` 里采集子进程的 OOM 打印很多，被 kill 的也是它，内存堆栈里卡住的还是它。`crash` 确认这些子进程同属一个 cgroup。

最后还有一条对照证据：**没出现 hang 的机器，都没有 OOM 报错。**

客户 B 的结论：

> Pod 的采集子进程在写 IO 时进 `__getblk()` 等待可用内存，只有拿到内存才能完成 `ext3_journal_stop()` 将 `t_updates` 递减，对应的 journal 内核线程才能被唤醒。但该 pod 内存已达上限且无可回收内存，进程触发了所在 memory cgroup 的 OOM；而引起 OOM 的进程因为申请不到内存无法从 `__getblk()` 退出到 `do_signal`，收不到 kill 信号释放内存，最终形成死环。

**这段描述是对的。** 机制链几乎没有问题。

## 三、但这个结论把因果压扁了

从上面这段能读出三层事实：

1. 服务器 hang 死是 OOM 触发的
2. OOM 是采集器触发的
3. **OOM 之后没有按预期结束，是内核的行为**

客户的结论只走到第 2 层就停了。

但第 3 层才是关键：**正常的 OOM 应该杀掉进程、释放内存、恢复。它没有。** 一个进程触发 OOM 是常规事件，操作系统每天都在处理；**OOM 之后锁死整机，不是任何应用程序应该有能力做到的事。**

所以准确的说法不是「采集器导致服务器 hang 死」，而是「**OOM 导致服务器 hang 死，采集器是 OOM 的来源之一**」。

这不是甩锅的文字游戏 —— 它决定了修复方向。如果是采集器的问题，改采集器就行；如果是内核的问题，**所有在这个内核上跑多进程 cgroup 限额的程序都有风险**，改采集器只是让概率降低，问题还在。

支撑这个怀疑的还有一条旁证：这个采集器已经在上百个项目、数十万台机器上跑了六七年，**从来没有出现过类似事故**。两家客户的操作系统恰好是同一个 RedHat 系衍生发行版。

## 四、先搜，搜到了，但对不上

带着「可能是发行版改内核引入的」这个怀疑去查，找到一篇记录同类问题的文章（[腾讯云开发者社区](https://cloud.tencent.com/developer/article/1880507)），复现过程和结论都有。它的结论是：

> RedHat 在内核 `3.10.0-862.el7` 引入的 BUG，之后的 el7 版本均未修复。与 **ext4** 文件系统有关。当多个进程使用同一个 cgroup 并触发 OOM 时，被内核杀死的进程无法处理信号，另一个进程申请不到内存，形成死锁。

**内核版本对得上（3.10），文件系统对不上 —— 那篇说 ext4，我们现场是 ext3。**

这一步是整个排查里唯一需要自己下判断的地方：**是放弃这条线索，还是认为它仍然适用？**

我的判断是适用，理由是：**这个死锁的关键不在 ext3 还是 ext4，在 jbd。**

ext4 用 jbd2，ext3 用 jbd，两者内部实现逻辑大体一致。死锁是 journal 事务机制造成的，而这套机制两边共用。

::: tip
「表面特征对不上」和「机制对不上」是两回事。
拿一篇现成分析去套自己的现场，**要核对的是机制链上的每一环是否成立，不是标题里的关键词是否一样。**
:::

下面按 ext3 展开，ext4 同理。

## 五、jbd 的事务，以及 `t_updates`

每个 ext3 文件系统对应一个 journal 实例，每次对文件系统的更新叫一个 handle。多个线程可能并发操作同一个 journal，jbd 为了保证一致性引入了事务 —— 时间上连续的多个 handle 合成一个 transaction。

一个 transaction 分两阶段：

**commit**
1. 用户线程获取 handle，取当前 running transaction，没有就创建
2. 递增 `t_updates`（表示这个事务正被多少个线程使用）
3. 把修改的数据加入 transaction 的 buffer 链表，**递减 `t_updates`**
4. 内核定期唤醒 journal 线程，把 running transaction 转为 committing，**然后等待 `t_updates` 归零**
5. buffer 链表合并写入 journal 区域
6. transaction 加入 checkpoint 等待列表

**checkpoint**
1. 从 checkpoint 列表取 transaction 的 buffer 数据
2. 写入物理磁盘

关键在第 4 步：**journal 线程会一直等 `t_updates` 归零。**

回看调用栈，发现调用了 `ext3_journal_start_sb()`，**但没有调用 `ext3_journal_stop()`**。

翻源码确认：`t_updates` 在 `ext3_journal_start()` 中递增，在 `ext3_journal_stop()` 中递减。**加上去了，没减下来。** 于是 journal 线程即使被唤醒也永远等不到归零，transaction 一直停在 committing。

## 六、死锁：两个进程互等

`t_updates` 不归零，说明 handle 还被某个进程持有着 —— 这个信息存在 `task_struct` 的 `journal_info` 里。

持有者就是那个 D 住的采集子进程。问题出在调用栈的 `ext3_get_blocks_handle()`：`__getblk` 申请不到内存，就一直调 `free_more_memory()` 释放再重试，拿不到就一直卡着。

于是两个进程锁死：

| | 进程 1（被 OOM Killer 选中） | 进程 2（持有 handle） |
|---|---|---|
| 状态 | `jbd_log_wait_commit()`，D 状态 | `__getblk()` 等内存 |
| 在等什么 | 等进程 2 的 transaction 完成 | 等内存被释放 |
| 为什么等不到 | 进程 2 拿不到内存 | 内存要靠杀掉进程 1 才能释放 |
| 为什么不被杀 | **D 状态收不到 kill 信号** | —— |

进程 1 被选中要杀，但它处在不可中断状态，**信号递不进去，内存就释放不了**；进程 2 等不到内存，事务结束不了，`t_updates` 不归零；进程 1 就永远等不到事务完成。

**两个进程都属于同一个 cgroup —— 这是闭环成立的前提。** 跨 cgroup 的话，进程 2 的内存申请不受进程 1 所在 cgroup 的限额约束，环就断了。

## 七、`__getblk` 本来应该拿得到内存

到这里还有一个问题没答：**内核为什么允许自己走进这个死锁？**

打破它其实很简单 —— 只要 `__getblk` 能申请到内存，事务就能完成，handle 就能放出来。也就是说，**只要允许这次分配突破 cgroup 限额就行**。

内核确实是这么设计的。从 2.6 起就有 `__GFP_NOFAIL` 标志：携带它的分配请求，内核会尽量满足，**不再理会 cgroup 的内存限制**。

翻 `__getblk` 的调用路径，在 `grow_dev_page` 之前，这个标志一直都带着。

**但从现象看，它没生效。标志在哪一步丢的？**

## 八、标志是在这一行丢的

对照 `3.10.0-693.el7` 和 `3.10.0-862.el7` 两个版本在该路径上的代码差异，发现后者在 `__add_to_page_cache_locked()` 里新增了一句 `mapping_gfp_constraint()`。

这个函数会把传入的 `gfp_mask` 与 `inode->i_mapping` 支持的 flags **按位与**。

根据 vmcore 分析确认：**`inode->i_mapping` 不支持 `__GFP_NOFAIL`** —— 上层一路传下来的标志，在这里被与没了。

而 Linux 主线代码历史上**从未在这个位置加过这行**。

倾向的判断是：RedHat 的维护者在移植上游 patch 时出了错。`mapping_gfp_constraint()` 本应作为 `add_to_page_cache_lru()` 的参数、针对部分操作传递，**而不是在随后的 `__add_to_page_cache_locked()` 里无条件执行**。

一行位置放错的代码，抹掉了一个「这次分配不许失败」的承诺，于是整条 `__GFP_NOFAIL` 的保护链断在了最后一米。

## 九、四个条件必须同时成立

```
① 内核 3.10.0-862.el7 及后续
   （el7 全系；4.14 仍受影响；5.4 之后已修复）
② RedHat 系发行版
   （包括但不限于 RedHat / CentOS 及各家衍生版）
③ 两个或以上进程共用同一 cgroup 内存限额，且有机会触发 OOM
④ 文件系统为 ext3 或 ext4
```

**四个全中才会发生，缺一不可。** 这也解释了为什么同一个采集器跑了六七年、数十万台机器都没事 —— 前两条是客户环境决定的，第四条是分区规划决定的，而第三条才是我们自己的。

它同时给出了三条互相独立的破解路径 —— **每条都只需要破坏其中一个条件**。

## 十、怎么处置的

### 应急

1. **提高采集进程的内存限额** —— 破坏条件 ③。不触发 OOM，死锁就不成立
2. **额外挂一个 xfs 文件系统，把进程单独部署过去** —— 破坏条件 ④。不走 jbd，死锁就不成立
3. **升级内核到 5.4 以上** —— 破坏条件 ①。根治，但代价最大

前两条是当场就能做的，第三条要排窗口期。

### 长期

1. **自动判断并规避**：采集器启动时检测内核版本、发行版与文件系统类型，四条命中就**强制关闭 cgroup 内存限额功能**
2. **换一套限额机制**：引入内存自监控 —— 发现子进程内存超过阈值一定幅度时，自动重启整个采集进程，用进程级重启替代 cgroup 级 OOM

第 2 条是这次事故真正的产品侧收获：**cgroup 的 OOM 是内核行为，我们无法控制它在什么内核上以什么方式结束；而自己重启自己是可控的。** 把限额从内核手里拿回到用户态，代价是精度变差，换来的是行为可预测。

## 尾声

结论最终获客户与云厂商内核团队认可，推动了内核热补丁。

这件事留下的东西，其实不在内核知识本身：

::: tip
**「A 触发了 B」不等于「A 应该为 B 负责」。**

采集器确实触发了 OOM，这一点从头到尾没有争议。但一个应用程序触发 OOM 是常规事件 ——
**它不应该有能力让整机 hang 死。** 中间那一步「OOM 之后为什么没有正常结束」，
才是真正要回答的问题。

被指认的时候，容易急着证明「不是我」。但更有用的动作是把因果链再往下拆一层，
**找出那个「本该发生却没有发生」的环节。**
:::
