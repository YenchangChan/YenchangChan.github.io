# 为什么不用 Kafka engine，也不写分布式表

> ClickHouse 自带 Kafka 表引擎，为什么还要在外面再做一个导入工具？
>
> 这两个问题看起来无关，其实是同一个问题的两面：**Kafka → ClickHouse 这条写入路径，该由谁控制。**

## 先把立场摆出来

**我是 [clickhouse_sinker](https://github.com/housepower/clickhouse_sinker) 的主要维护者，我在推荐我自己维护的东西。**

所以这篇不假装中立。但按这一栏的约定，**代价我会说得比优点更细** —— 包括我推荐的这条路自己的代价，那部分在第四节。

## 一、需求到底是什么

先说清楚要解决的是什么，否则很容易变成「我的工具功能更多」。

日志与指标场景下，Kafka → ClickHouse 这条链路要同时满足：

1. **高吞吐大批量写入** —— MergeTree 的性能来自 merge，每次 INSERT 产生一个 part，小批次写入会把 part 数量顶起来，merge 压力跟着涨。官方建议单次 1w～50w 行
2. **数据落在集群里是均衡的** —— 不能某个节点磁盘先满
3. **可以按业务语义路由** —— 去重字段、join key、聚合维度落在同一个分片上（[为什么这件事重要](/clickhouse/tooling/why-not-auto-rebalance)）
4. **副本故障时写入不中断** —— 分片内某个副本挂了，自动切到同分片的其他可用副本
5. **至少一次语义** —— 数据确认写入成功之后才提交 offset

这五条里，**第 2、3、4 条是官方 Kafka engine 做不到的**，而且不是「做得不够好」，是能力上没有。

## 二、Kafka engine 的代价

### 它决定了表在内存里的排布

在 ClickHouse 里，engine 决定了一张表的数据在内存中怎么组织，直接影响读写能力。

**MergeTree 家族是唯一有极致读写性能的那一支** —— 稀疏索引、分区裁剪、compaction、TTL 分层，这些全在 MergeTree 上。

用 Kafka engine 意味着数据先进一张不是 MergeTree 的表，再靠物化视图转进 MergeTree。**多一跳，而且这一跳的行为你控制不了。**

sinker 是直接写 MergeTree 本地表 —— **专为 MergeTree 设计，数据一步到位。**

### 它依赖第三方库，出问题排障困难

官方 Kafka engine 底层用的是 **librdkafka**。库本身质量不差，但它是嵌在 server 进程里的第三方组件：

- 出了问题，日志在 server 日志里和其他东西混在一起
- 消费行为的可观测性受限于 engine 暴露了什么
- 想调一个 librdkafka 的参数，得看 ClickHouse 有没有把它透出来

**懂的懂，不出问题还好，一旦出了问题，根本无法进行有效排障。**

而外部工具是一个独立进程：日志独立、指标独立、可以单独重启、可以 pprof。

### 它无法做集群内的均衡写入，也没有 sharding policy

这是最硬的一条。

Kafka engine 部署在每个节点上，各自消费各自的分区。**数据落在哪个节点，取决于 Kafka 分区分配的结果，不取决于数据本身。**

于是：

- 均衡与否听天由命 —— Kafka 分区数据量不均，ClickHouse 节点就不均
- **完全没有按业务语义路由的能力** —— 你无法让同一个去重 key 恒定落在同一分片

### 副本挂了，写入可能整体卡住

分片内某个副本不可用时，**官方 engine 没有机制保证自动切换到同分片内其他可用副本**，可能整个写入就卡在那里。

sinker 的做法是：配置里 hosts 是两层数组（外层 shard、内层 replica），某个副本不可用时自动切到同分片内的其他副本。

## 三、为什么写本地表而不是分布式表

即使不用 Kafka engine，还有一个选择：外部工具写 Distributed 表，让 ClickHouse 自己分发。

我也不这么做。

### 分布式表 INSERT 实际发生了什么

默认异步模式下（`insert_distributed_sync = 0`）：

```
① 数据先全量落到「接收节点」的本地临时目录
   data/<db>/<table>/shard1_replica1/ 等，按分片键拆开
② 后台线程异步把各分片的数据发送到对应节点
③ 每个分片收到后，若是 ReplicatedMergeTree，
   再经 Keeper 在副本间复制
```

三跳。而不是一跳。

### 三个代价

**① 节点间磁盘使用不均**

接收节点要先承载**全部**数据，再往外分发。分发需要时间，数据量大时**极易造成某一个节点磁盘占用异常高**。轮询接收节点能缓解，但缓解不等于消除 —— 峰值时刻的压力仍然全压在当班那个节点上。

**② Keeper 压力**

写入批次越小，产生的 part 越多，每个 part 都要走一遍 Keeper 的复制协调。

写入量大且批次小的时候，**Keeper 会进入极度繁忙状态**。一旦某次操作 30 秒得不到响应，表会进入 `READ_ONLY` —— 整张表停写。

> 这条我在另一篇里有完整的生产案例：[126 万 znode 是怎么长出来的](/clickhouse/troubleshooting/keeper-async-blocks)。Keeper 的负载是 ClickHouse 集群里最容易被低估的一项。

**③ 集群内网络带宽**

数据在集群内多走一跳，占的是内网带宽 —— 而查询也要用同一条内网做分片间的数据交换。**写入挤占查询带宽，这个影响在压测里很难暴露，在生产的高峰期才会出现。**

### 写本地表怎么解决

外部工具在**写入之前**就算好每一行该去哪个分片，然后直连那个分片的节点写本地表。

```
sinker 算好分片  →  直连目标分片写本地表  →  分片内副本复制
```

接收节点不存在了，中转也不存在了。**① 和 ③ 直接消失，② 因为批次大（默认 `bufferSize` 26 万行）而大幅缓解。**

## 四、我推荐的这条路，代价是什么

**这一节不能省。** 上面三节说的都是别人的代价。

### 你得自己承担路由和均衡

sinker 把 sharding 规则拿到了写入侧，好处是可以按业务语义路由，**代价是这个规则从此归你维护**：

- 分片数变了，路由规则跟着变，**存量数据需要 rehash** —— 这是个很重的操作
- 规则写错了，数据就分布错了，而且**不报错**

### 指定了 shardingKey 之后，故障域变了

这是最实在的一条代价：

::: warning
**如果一个分片内的所有副本全部挂掉，那么路由到这个分片的数据将永远无法写入**，
sinker 会一直失败，直到集群恢复。

没指定 shardingKey 时（按 offset 均摊），理论上可以把这批数据改投到别的分片。
**指定了之后不行 —— 改投就意味着路由规则被破坏了。**
:::

换句话说：**按业务语义路由换来的查询优化，代价是把可用性从「集群级」降到了「分片级」。**

### 多了一个要运维的组件

sinker 是独立进程，要部署、要监控、要升级、要管配置（本地文件或 Nacos 托管）。Kafka engine 至少不用管这些 —— 它就在 server 里。

**一套新组件带来一整套新的故障面**，这个账要算全。

## 五、我会选什么，以及什么情况下我会改主意

**规模化的日志与指标写入，我选外部工具写本地表。** 上面五条需求里有三条是官方 engine 做不到的，而这三条恰好都是规模变大之后才致命的。

**什么情况下我会改主意：**

| 情况 | 选择 |
|---|---|
| 集群只有一个分片 | **Kafka engine 或分布式表都行。** 前面说的均衡、路由、分发三个问题全部不存在，这时候多一个组件是纯粹的负担 |
| 写入量小、批次天然就大 | **分布式表够用。** Keeper 压力和磁盘不均都出不来，让 ClickHouse 自己分发省事得多 |
| 团队没有能力维护额外组件 | **用 engine。** 一个跑得不稳的外部工具，比一个能力有限但简单的内建方案更糟 |
| 数据没有任何业务语义上的分片需求 | **差异大幅缩小。** 这时选外部工具的理由只剩下可观测性和排障便利，不再是「做不到」 |

::: tip
把这四行倒过来读，就是我推荐外部工具的真实前提：
**多分片、大写入量、有业务语义的分片需求、且团队养得起一个额外组件。**

四条同时成立，这个选择才明显更优。缺一条，账就要重新算。
:::
