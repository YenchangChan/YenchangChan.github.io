## 一、开场：拿 OpenObserve 官方自己的样例数据

为了杜绝「你是不是故意挑了对 O2 不利的数据」这种质疑，第一组实测**直接用 OpenObserve 官方发布的样例数据集**：

- **数据集**：k8s 容器日志（JSON），OpenObserve 官方样例
- **下载**：`https://zinc-public-data.s3.us-west-2.amazonaws.com/zinc-enl/sample-k8s-logs/k8slog_json.json.zip`
  （`zinc-*` 是 OpenObserve 前身 ZincObserve 的命名，确系官方数据）
- **解压后大小**：**8.40 MiB**（`k8slog_json.json`）

这是一份典型的 k8s 日志：字段高度重复、结构规整、熵极低——也就是**最有利于压缩、最能撑起「百倍压缩」叙事**的那类数据。我们就从这份「对 O2 最友好」的数据开始。

### 1.1 完整对照表（同一份 8.40 MiB 数据）

| 方法 | 数据 | 索引 | **合计** | 说明 |
|---|---|---|---|---|
| `zstd -19` 单文件 | 53.4 KiB | — | 53.4 KiB | 通用压缩极限（O2 的 level 写死、用不到这一档） |
| `zstd -1` 单文件 | 79.3 KiB | — | 79.3 KiB | 与 O2 默认 zstd level 对齐 |
| **O2** | 80 KB（0.08M） | 100 KB（0.1M） | **184 KB** | 数据部分几乎等于 `zstd -1` |
| **ClickHouse** | 70.53 KB | 132.02 KB | **202.55 KB** | 数据更小，但索引开销更重 |

> ⚠️ **口径提醒**：CH 侧务必把**二级索引**算进去。只看 `data_compressed_bytes`（70.53 KB）会漏掉 132.02 KB 的索引，得出完全相反的结论——这是我们在这次实测中真实踩过的坑。

> 复现命令：
> ```bash
> zstd -19 k8slog_json.json    # → 53.4 KiB
> zstd -1  k8slog_json.json    # → 79.3 KiB
> ```
> O2：默认配置导入，读 stream 统计的 `storage_size` / `index_size`。
> CH：`zstd-1` 压缩、对 log 字段建全文索引，读 `system.parts` 的 `bytes_on_disk`（含索引）。

### 1.2 从这张表能读出什么

**① O2 的列存净增益 ≈ 0。**
O2 的数据落盘 ~79 KiB，和你在命令行敲一句 `zstd -1` 得到的 79.3 KiB **几乎逐字节相同**。也就是说，O2 那套「列存 + Parquet + 排序 + 编码」在这份数据上的压缩贡献**约等于零**——列式编码省下的，恰好被 Parquet 元数据 + 小文件固定开销吃掉。**O2 的「压缩」 = 一个 `zstd -1` 命令，没有魔法。**

**② O2 把 34% 的压缩空间锁死了。**
`zstd -19` 能压到 53 KiB，但 O2 的 zstd level **写死在 ~1**（源码确认，为换摄入速度），**你想调到 -19 都没有入口**。省下的空间，O2 主动放弃、且不给你选择权。

**③ 一旦开全文检索，O2 的存储直接翻 2.3 倍、压缩率从 108x 崩到 47x。**
Tantivy 全文索引**不压缩**，导致索引（100 KB）**比数据本身（80 KB）还大**，合计 184 KB。这不是 bug，是架构必然——也印证了社区 issue 里「索引反超数据」的报告。

**④ 但这一局，O2 反而略胜。**
功能对等（都建全文索引）下：**O2 184 KB vs CH 202.55 KB——O2 小约 9%。**

原因不在数据侧（CH 数据 70.53 KB 比 O2 的 80 KB 还小 12%），而在**索引开销的占比**：CH 的全文索引 132.02 KB 是其数据的 **1.9 倍**，O2 的索引 100 KB 是其数据的 **1.25 倍**。**在这么小的数据量上，谁的索引更「重」，谁就输。**

> 这条结论很重要，它推翻了一个想当然的判断：**并不是「CH 什么场景都压得更小」。小数据量 + 需要全文检索的场景，O2 的总占用反而更优。** 真正的分水岭出现在大数据量上——见第二章。

### 1.3 一个必须说清的前提

这份数据只有 8.40 MiB，是**小文件、列存的劣势区**（Parquet 元数据占比偏高），而且量级太小、索引固定开销占比过高。**它能锁定的结论是有限的**，只有一条是确定的：

> **O2 没有「压缩黑科技」——它的数据侧落盘（80 KB）就等于一个 `zstd -1` 命令（79.3 KB），列存净增益约等于零。**

至于「谁的总占用更小」，这一组给出的答案（O2 略胜 9%）**不能外推到生产规模**：它高度依赖数据量和索引方案的固定开销占比。真正的分水岭在大数据量上——那里 CH 的列存编码（LowCardinality、per-column codec、`ORDER BY` 聚类）才会显现，见第二章。

**同时也要澄清一个常被误引的说法**：「140x」是拿最臃肿的 Elasticsearch 当分母得来的，**它从来不是对 ClickHouse 的优势**——O2 官方也从未发布过 vs ClickHouse 的对比（维护者已公开承认不存在）。

## 二、大数据实测：27.3 亿行 GitHub Events

第一章是「最好情况」（数据软、压缩率虚高、量级太小）。这一章是真实生产量级的数据。

- **数据集**：GitHub Events，**2,734,244,238 行 / 54 列**——**ClickHouse 官方公开示例数据集**（[GitHub Events Dataset](https://clickhouse.com/docs/getting-started/example-datasets/github-events)），任何人都能自行下载复现
- **O2 版本**：v0.91.1，8 个写入线程，S3 后端
- **对照原则**：同一批数据、同样的行数（CK 两次均为 119 个成功 INSERT、总行数完全一致；O2 只统计最终成功的主迁移，排除失败尝试）

**先说清楚语义对等**，否则后面所有数字都会被误读：

> O2 的全文索引是 **Tantivy 分词倒排 = token 语义**。所以**功能对等的 CK 配置是 `text(tokenizer=splitByNonAlpha)`**。
> CK 的 `ngrams(5)` 支持**子串匹配**，能力**强于** O2，拿它比是对 CK 不公平；`ngrambf_v1` 是概率型索引（有假阳性），能力**弱于**精确倒排。三者不可混为一谈。

### 2.1 存储：功能对等下 CK 小 25%

全文单位统一为 **GiB**（二进制，1 GiB = 1024³ 字节），与 CK `formatReadableSize` 一致。

| 方案 | 数据 | 索引 | **合计** | vs O2 |
|---|---|---|---|---|
| **O2**（Tantivy 全文索引） | 174.64 GiB | 45.14 GiB | **219.78 GiB** | 基准 |
| **CK `text(splitByNonAlpha)`**（对等） | 117.32 GiB | 46.80 GiB | **164.12 GiB** | **小 25%** |
| CK `ngrambf_v1`（概率型） | 105.64 GiB | 12.23 GiB | 117.87 GiB | 小 46% |
| CK 无二级索引 | 105.58 GiB | 0 | 105.58 GiB | 小 52%（无全文检索） |
| CK `text(ngrams(5))`（子串，能力更强） | 106.05 GiB | **417.81 GiB** | **523.86 GiB** | 大 138% |

> 上表为同一轮测量。三天后（2026-07-21）随查询压测重新取数，得到 **CK 163.97 GiB**（117.20 + 46.77）、**O2 218.72 GiB**（173.85 + 44.87）——两边都略微变小，来自 compaction 继续推进。差异在 0.5% 以内，不影响任何结论；本文统一采用上表这一轮的数字以保证表内可比。

**两个关键读数**：

1. **O2 的索引效率不差，差在数据列。** 功能对等下索引几乎一样（45.14 vs 46.80 GiB），但数据列 **CK 117.32 GiB vs O2 174.64 GiB——CK 小 33%**。这是 CK 列存编码（`LowCardinality`、per-column codec、`ORDER BY` 聚类）在真实高熵数据上的实打实增益，也是 O2「排序键写死、不能逐列调 codec」的代价。
2. **「精确子串匹配」是全场最贵的能力**：`ngrams(5)` 索引 417.81 GiB，是其数据的 **3.9 倍**。想省空间就得退回概率型（12.23 GiB，接受假阳性）或 token 语义（46.80 GiB，放弃子串）。**CK 让你在这条光谱上选，O2 只有一个固定点。**

> ⚠️ **不要比「压缩率倍数」**：O2 报 `3.08 TiB → 174.64 GiB ≈ 18x`，CK 报 `792.69 GiB → 105.58 GiB ≈ 7.5x`，看起来 O2 赢，但 CK 落盘更小。原因是分母口径完全不同（O2 的 `original_size` 是 flatten 后重新序列化的 JSON 文本，逐行重复所有字段名；CK 是列式二进制未压缩值）。**只比绝对落盘字节数。**

### 2.2 写入吞吐：功能对等下 CK 快 **18 倍**

| 写入目标 | 耗时 | 行吞吐 | 字节吞吐 | 相对 O2 |
|---|---|---|---|---|
| **O2**（8 workers） | **14h38m41s** | 51,863 行/s | 67.23 MiB/s | 1× |
| CK `ngrams(5)`（能力更强） | 3h19m21s | 228,597 行/s | 77.3 MiB/s | 4.41× |
| **CK `splitByNonAlpha`**（对等） | **48m57s** | **930,965 行/s** | 318.9 MiB/s | **17.95×** |

**行吞吐差 18 倍，字节吞吐却只差 4.7 倍**——因为两边每行传输量根本不同：

| | 每行字节 |
|---|---|
| O2（JSON bulk） | **1,359 B/行** |
| CK（列式写入） | ~355 B/行 |

O2 共发送 **3.38 TiB** JSON 请求体（与其内部 `original_size` 3.08 TB 相差约 20%，正好是 bulk API 每条记录前那行 action metadata 的开销——两个独立来源互相印证）。

> **但「字节吞吐接近」不能为 O2 开脱，它只是把瓶颈定位清楚了**：O2 不是处理字节的能力弱，而是**协议本身低效**——同样的信息量要传 3.8 倍的字节。而这不是使用者的选择：**JSON bulk 就是 O2 的主要摄入路径**，你没有更省的协议可用；CK 那边可以走 Native 二进制、列式批量、Parquet 直读。**协议低效是架构的一部分，不能摘出去算。**

### 2.3 资源消耗：CK 每核效率是 O2 的 10 倍，但 O2 内存省 3.6 倍

| 写入任务 | 进程 CPU 平均/P95 | 进程 RSS 平均/P95 | 峰值 RSS | 整机 CPU 平均/P95 |
|---|---|---|---|---|
| **O2** | **4.01 / 5.83 核** | **2.90 / 3.75 GiB** | **5.61 GiB** | **14.39% / 20.61%** |
| CK `ngrams(5)` | 11.23 / 33.29 核 | 13.21 / 17.43 GiB | 93.95 GiB | 38.62% / 63.20% |
| CK `splitByNonAlpha` | 6.94 / 15.53 核 | 10.46 / 14.64 GiB | 17.15 GiB | 45.42% / 59.00% |

换算成**每核吞吐**（排除资源投入差异，最公平的效率指标）：

| 任务 | 每核吞吐 | 相对 O2 |
|---|---|---|
| O2 | 12,944 行/s/核 | 1× |
| CK `ngrams(5)` | 20,356 行/s/核 | 1.57× |
| **CK `splitByNonAlpha`** | **134,145 行/s/核** | **10.36×** |

**三个结论**：

1. **差距不是靠堆资源堆出来的。** CK 只多用了 **73% 的 CPU**（6.94 vs 4.01 核），却快 **17.95 倍**——每核效率相差 **10.4 倍**，是效率的代际差异。
2. **O2 没吃满硬件。** 8 workers 只跑到 4.01 核、整机 CPU 仅 14.39%——**瓶颈不在 CPU**（这一点在 §2.4 被进一步坐实）。
3. **但内存上 O2 是明显赢家**：平均 **2.90 GiB**，CK 要 10~13 GiB。这是 O2 的真实优势，也解释了它在小规模、资源受限、边缘部署场景的生存空间。**资源换吞吐的账是：CK 用 1.7× CPU + 3.6× 内存，换 18× 吞吐。**

> ⚠️ 采样口径差异：O2 约 10 秒采样，CK 历史指标约 1 秒采样（故 CK 的 P95/峰值更容易捕捉到瞬时尖峰，如 ngrams 的 93.95 GiB 只是约一分钟的瞬时值，P95 的 17.43 GiB 更有代表性）。另：O2 迁移时源端 CK 还占用约 0.21 核 / 4.60 GiB。评价单项写入效率应优先看**进程 CPU**而非整机。

### 2.4 给 O2 最后一次机会：memtable 分桶对照实验

既然 O2 没吃满 CPU，**「是不是没调好」必须排除掉**，否则 18 倍会被质疑。

**先纠正一个已失效的调优项**（这本身就是个坑）：

> 大量资料（含**官方性能文档至今仍在推荐**）会让你开 `ZO_FEATURE_PER_THREAD_LOCK=true`。但该参数**已于 2025-09 被移除**（[commit 3a1aaa0](https://github.com/openobserve/openobserve/commit/3a1aaa0707258d7b08625c11175a05ba744456e2)），在 v0.91.1 上设置它会被**静默忽略**——不报错、也不生效。等价能力由 **`ZO_MEM_TABLE_BUCKET_NUM > 1`**（memtable 分桶，降低写入锁竞争）接管。
>
> **照官方文档调优，你会得到一个「什么都没发生」的结果，却以为已经优化过了。**

于是按当前版本的真实等价项做对照：**baseline `bucket=1` vs 优化 `bucket=5`**（5 是该功能原始官方示例值），完全相同的数据、8 个写入线程、独立 S3 前缀。

| 指标 | bucket=1 | bucket=5 | 变化 |
|---|---|---|---|
| 数据量 | 14,868,852 行 | 14,868,852 行 | — |
| 写入用时 | 383 s | 380 s | — |
| **吞吐** | 38,822 行/s | 39,129 行/s | **+0.79%** |
| O2 平均 CPU | 3.70 核 | 3.65 核 | 几乎不变 |
| **O2 平均 RSS** | 2.49 GiB | 3.48 GiB | **+39.4%** |
| 写入期 Parquet GET | 124 | 304 | +145% |
| **写入期 Parquet PUT** | 1,164 | 3,034 | **+161%** |
| **S3 最终对象数** | 2,807 | 8,355 | **+197.7%** |
| S3 最终字节 | 2.459 GB | 2.426 GB | −1.35% |
| compaction 期 CPU | — | — | **+29.7%**，峰值 3.66 → **8.73 核** |

**结论：这是一次净负面的「优化」。**

用 **+39% 内存、+161% PUT 请求、+198% 对象数、+30% compaction CPU**，换来 **0.79% 的吞吐提升——在噪声范围内**。而这恰好印证了官方文档自己的警告：低吞吐场景会产生更多小 WAL 文件。

**更重要的是它排除了两个嫌疑，把瓶颈钉死了**：

- ❌ **不是 memtable 锁竞争** → bucket 从 1 加到 5，吞吐纹丝不动
- ❌ **不是 CPU 不足** → 始终只吃 3.7 核，整机大量闲置

> **那只剩上游的串行化：HTTP / JSON 解析、schema 推断、flatten。** 这与「O2 每行传输 1,359 字节 vs CK 355 字节」的观测完全吻合——**瓶颈在协议与解析层，是架构选择，不是配置能救的。所以 §2.2 那个 18 倍是硬的。**
>
> 我们主动给了 O2 最好的机会去反驳这个结论，它没有接住。

**一个反预期（我们此前的猜测错了）**：原以为「小文件变多会拉低压缩率」，实测是**对象数 +197.7%，字节数只 −1.35%**——压缩率几乎没变。说明在这个量级上 Parquet 的 row group/字典效率对文件数不敏感，**代价全部转嫁到 S3 请求数与 compaction 负担上，而非存储体积。**

### 2.5 compaction 实测：确实发生在对象存储上

这是把「源码推断」升级为「实测证据」的一环。

- **写完后请求仍在持续**：客户端停止写入后，S3 请求并未停止。基线组写完后 10 分钟内仍有 **474 次 Parquet GET + 275 次 PUT**；bucket=5 组更多，**1,417 GET + 1,226 PUT**。
- **日志直接坐实**：O2 日志明确记录 `[COMPACTOR:WORKER]` 读取旧文件并合并生成新 Parquet。
- **未观察到 DELETE**：因为默认**延迟删除时间为 2 小时**，而观察窗口只有 10 分钟——这正好对上源码里「file_list 软删除 + 延迟物理清理」的两段式设计。
- **对在线写入的影响很小**：直接比较时间窗口会得到「下降 21%–29%」，但那是 source part 逐渐写完、并发降低造成的**时间混杂**；**按相同活跃 source-part 并发度校正后，基线 −0.15%、优化组 +1.54%**——净影响在 **2% 以内**。

> **所以 compaction 的代价不在「拖慢写入」，而在后台资源与 S3 请求数**：bucket=5 场景下 compaction 期 CPU 平均 +29.7%、峰值飙到 8.73 核，S3 请求量翻倍。**这正是「140x 存储成本」那笔账里从不出现的部分。**

### 2.6 S3 单盘瓶颈：单流已无并发余量

本轮 S3 后端是 `192.168.101.95:59000` 上的单个 RustFS 实例。容器挂载链路经宿主机实查确认如下：

```text
RustFS /data
  → /data01/data/container/rustfs
  → /data01
  → /dev/sda（ext4，PERC H730P RAID 虚拟盘）
```

RustFS 的 `/logs` 和 Docker 数据目录也位于 `/data01`，即数据、日志和容器运行时共享同一块 `/dev/sda`。O2 单流持续写入期间，该盘观测到 **97.5%~98.3% util、约 300~370 read IOPS、5~6 MiB/s 读取、12~14 ms await**，而整机 CPU 仍有约 **92% idle**。这不是顺序带宽耗尽，而是典型的小块随机 I/O/延迟瓶颈。

同期抓包显示 O2 对 S3 的 PUT 请求体约 **4.15 MiB/s**，能够解释写压力；但 O2 的 GET 数量不足以解释全部读 IOPS，额外读取还可能来自 RustFS 后台对象扫描、元数据操作或同盘其他容器。因此，不能把 `/dev/sda` 的全部读负载都归因于 O2。

这个结果意味着：**当前单表负载已经几乎耗尽 S3 后端的 I/O 余量**。若 10 张或 100 张同等负载的表同时写入并触发 compaction，请求会叠加 GET、PUT、DELETE 和小对象元数据操作；总吞吐不会随表数线性增长，排队延迟、超时与重试反而可能形成正反馈，最终表现为 S3 严重降速或阶段性不可用。按当前单表约 4.15 MiB/s 的 PUT 量粗算，10/100 张分别要求约 41.5/415 MiB/s 的纯写入请求体，尚未计入 compaction 的读写放大，当前单盘架构没有安全承载余量。

> ⚠️ **边界必须说清楚**：这是「单 RustFS、单目录、单 RAID 虚拟盘，且日志与 Docker 数据同盘」这套测试环境的容量上限，**不能直接外推为 O2 软件本身的集群上限**。反过来，本轮 O2 吞吐也已经包含这个 S3 磁盘瓶颈，不能当作理想对象存储条件下的 O2 写入上限。正式评估 10~100 个高吞吐流，需要使用多盘 SSD/NVMe 或分布式对象存储，并单独测量并发 compaction 下的 S3 P95/P99 延迟、队列深度、错误率与重试量。

### 2.7 本章小结

| 维度 | 结论 |
|---|---|
| **存储**（功能对等） | CK **小 25%**（164.12 vs 219.78 GiB）；O2 索引效率不差，**差距全在数据列（CK 小 33%）** |
| **写入**（功能对等） | CK 快 **17.95 倍**；每核效率差 **10.4 倍** |
| **内存** | **O2 胜**：2.90 GiB vs CK 10.46 GiB（省 3.6 倍） |
| **可调优性** | O2 的写入瓶颈**不是配置能救的**（bucket 调优净负面）；CK 提供从 105→524 GiB 的完整索引光谱 |
| **隐藏成本** | compaction 在对象存储上持续产生 GET/PUT，写完 10 分钟内仍有数百次请求；DELETE 延迟 2 小时 |
| **扩展边界** | 当前单表已使 RustFS 数据盘达到约 98% util；10/100 个同等负载流无法由这套单盘 S3 架构安全承载，但该结论不等同于 O2 集群软件上限 |

### 2.8 查询性能：27 场景三端对照

**测试对象是三个端点**：CK `github_events_text_zstd_split`（27.3 亿行，全列 ZSTD(1) + `splitByNonAlpha` 全文索引）、O2 本地盘 `github_events_text`（27.3 亿行）、O2 S3 `github_events_text_s3`（18.8 亿行，截止约 2019-10）。时间范围只取三端都有数据的 2017/2018 区间，左闭右开，`file_time` 与 `_timestamp` 对齐。CK 关闭 query result cache，每次 O2 查询前删除该流结果缓存。27 个场景 × 3 端 = 81 次 cache-bypass 查询全部成功。

> **前一轮查询测试已作废，原因写在这里备查**：上一版用了 `ILIKE`。`ILIKE` 在任何索引上都**不走索引**——EXPLAIN 里连 `Skip` 段都不出现，测到的是 CK 全表扫描 27.3 亿行的耗时，不是引擎能力。同表 `hasToken` 能把 granule 从 346,381 剪到 **14**（剪枝 99.996%），差了四个数量级。**跨引擎比查询，第一件事是确认两边真的走了索引。**

#### 先说最严重的：O2 返回了错的聚合结果，而且说自己是对的

这是本轮最重要的发现，它不是性能问题：

```
同一份数据、同一时间范围（2018-05-01 ~ 2018-05-08）：

  总行数                                    三端一致  7,405,699      ✅
  直接过滤 IssueCommentEvent
    AND repo_name='ant-design/ant-design'   三端一致  4,063          ✅
  ──────────────────────────────────────────────────────────────────
  GROUP BY event_type, repo_name
    ORDER BY count DESC LIMIT 100
        CK / O2 本地：4,063        O2 S3：4,053   ← 少 10 条
        且 API 同时报告 is_partial = false        ← 声称结果完整
```

排除法：**不是 SQL 写法差异**（同一条件直接过滤三端一致），**不是行数缺失**（总数一致），**不是 tokenizer 语义**（这条查询不含全文匹配）。

> ⚠️ **首轮排除法里有一步是错的，值得记下来。** 当时还检查了「按 `event_type` 一级分组，三端每组完全一致 ✅」，并据此判断「低基数分组没问题、只有高基数才出错」。**后续复测推翻了这一条**——同一时间范围内，5082 的 `event_type` 分组同样是错的（`PushEvent` 分组值 4,193,787 vs 直接过滤 4,285,567）。
>
> 这个假阴性把追查方向带偏了：它让我们以为问题局限在「高基数组合」这种边缘场景，从而低估了严重性。**真实情况是低基数分组一样中招**——而低基数分组恰恰是生产里最常用的。

**顺着这条线追下去，两次归因都错了，最后靠动手实测才定位。**

##### 追查过程：两次归因错误，都被实测推翻

这一段值得完整记录，因为**两次错误的归因都很有说服力，都是靠动手测才推翻的**。

**第一次错误：归因给 S3。** 最初的结论是「O2 S3 后端高基数聚合有缺陷」，理由是本地端正确、S3 端错误。判别实验：在**同一个 5082 实例、同一个 S3 后端**上，只改分组字段——

| 测试 | 分组字段 | 是否 ∈ index_fields | 结果 |
|---|---|---|---|
| C | `event_type`（12 个值） | ✅ | ❌ 差 -91,780 |
| D | `actor_login`（高基数） | ❌ | ✅ **完全一致** |
| E | `repo_name`（高基数） | ✅ | ❌ 差 -60 |

**非索引字段 100% 正确，索引字段全错。S3 就此洗清**——真正的变量是 `index_fields` 配置。而我们两个端点恰好在这一点上不一致：**5082 配了 `index_fields=[event_type, repo_name]`，5080 是空的**，而这两个字段正是出问题那条查询的分组字段。

**第二次错误：归因给 compaction 滞后。** 既然索引只在 compaction 阶段生成，那「未 compaction 的数据没索引、因此在分组里蒸发」看起来顺理成章。但这个推论有个前提没验证——写入 13:30 就停了，四个半小时后还会有未 compaction 的数据吗？

查 `file_list` 元数据的结果是：

```
2018-05 时间段     757 个文件    index_size=0 的：0
2018-01 时间段   4,125 个文件    index_size=0 的：0
全流           205,835 个文件    index_size=0 的：0     索引覆盖率 100%
```

**一个缺索引的文件都没有。** 这条推论当场作废。

> **教训**：两次都是「机制听起来合理」就当成了结论。第一次靠判别实验推翻，第二次靠查元数据推翻。**源码能告诉你代码怎么写的，但告诉不了你线上跑成什么样。**

##### 实际机制：跨文件合并时丢数据，且没有安全阈值

排除法做完后，剩下的变量是**查询跨越的文件数**：

| 查询跨度 | 文件数 | 返回分组数 | 行数覆盖 |
|---|---:|---:|---:|
| 1 小时 | 4 | 12 | **100.00%** ✅ |
| 6 小时 | 24 | 12 | **100.00%** ✅ |
| 1 天 | 96 | 12 | **100.00%** ✅ |
| 7 天 | 757 | **7** | **82.87%** ❌ |
| 31 天 | 4,125 | **3** | **29.33%** ❌ |

**注意这里的量级**：`event_type` 实际只有 12 个不同值，一条 31 天的 `GROUP BY event_type` **只返回了 3 个分组、丢了 70.67% 的行**，而 `is_partial=false`。这已经不是「高基数 Top-N 少算几行」，是**基础聚合查询返回严重残缺的结果还声称完整**。

**提高 LIMIT 只能缓解，找不到安全阈值**（同为 31 天范围）：

```
LIMIT  100 →  3 组  29.33%          LIMIT 1000 →  6 组  68.84%
LIMIT  500 →  5 组  46.43%          LIMIT 2000 →  9 组  93.13%   ← 仍然错
LIMIT  999 →  6 组  68.80%
```

所需 LIMIT 随文件数增长：757 文件时 LIMIT 1000 已经够，4,125 文件时 2000 还不够。原始的 G02 查询也一样——LIMIT 100 差 11、LIMIT 1000 差 2、LIMIT 5000 才对。

**而你无法事先知道该设多大：要知道，就得先知道正确答案。**

相关源码是 `src/config/src/tantivy/query/topn_collector.rs` 的 `TopNSegmentCollector::harvest`——超过 `ZO_INVERTED_INDEX_TOPN_MAX_GROUP_NUM`（默认 1000）时调用 `select_top_k_dense()` 只保留本文件局部 Top-K，注释自述 「the merged top-n becomes approximate」。**但实测丢失比这个阈值所能解释的更严重**（`event_type` 仅 12 组，远低于 1000，照样丢），完整机制需由官方定位。

> 📮 **已上报官方**：[openobserve/openobserve#13363](https://github.com/openobserve/openobserve/issues/13363)。本节的复现步骤、文件数-丢失率对照、LIMIT 扫描、以及「与存储后端无关 / 与 compaction 无关」两项排除，均已附在该 issue 中。后续进展以官方回复为准。
>
> **一个独立佐证**：后续（2026-07-22）用 GreptimeDB 跑同一份 4.5 亿行数据、同一条高基数 Top-N 查询，**结果与 ClickHouse 完全一致、正确**。GreptimeDB 与 O2 架构高度同构（都是 Rust + Parquet + Puffin + Tantivy），它算得对，进一步排除了「数据本身有问题」或「tokenizer 差异」——**缺陷是 O2 的 `TantivyOptimizeExec` 近似路径特有的**。

##### 最新版本仍未修复

```
topn_collector.rs   v0.91.1  vs  main (v0.93.0, HEAD 99c571b)
                    diff 输出为空（字节级完全相同）
ZO_INVERTED_INDEX_TOPN_MAX_GROUP_NUM 默认值 1000      两版一致
```

演进时间线全部早于 v0.91.1：PR #12348 引入 → PR #12528 因性能问题临时禁用 → **PR #12574 用当前这套 flat ordinal collector 重写并重新启用**，此后未再改动。

##### `is_partial` 结构性地覆盖不到它

追完整条赋值链（`cluster/flight.rs::search` → `cluster/http.rs::search` → `Response::set_partial`），`partial_err` 只有两个来源：**搜索超时/取消**、**返回行数超默认展示上限**。近似降级路径里唯一的痕迹是一条 `log::debug!`，默认日志级别下完全看不见。

> ⚠️ **所以这是两个需要分别修的缺陷**：① Top-N 静默降级为近似；② `is_partial` 无法反映这件事。
>
> 第二条并非孤例——O2 官方 issue **#6311**（2025-03-19 提出，**至今 open**）报告了 `is_partial` 在 VRL 函数报错时同样不置位，2026-05-06 的验证评论写着 **「Root cause — STILL UNFIXED」**，并指出 `src/service/search/cluster/http.rs:124` 设置了 `function_error` 却没设 `is_partial=true`。
>
> **也就是说，`is_partial=false` 作为「结果完整」的承诺，目前在至少两条独立路径上失效。**

##### 有绕法，但绕不掉「无法验证」

| 解法 | 代价 |
|---|---|
| 调高 `ZO_INVERTED_INDEX_TOPN_MAX_GROUP_NUM` | 官方注释自述 「trade speed for accuracy」 |
| 把 GROUP BY 字段移出 index_fields | 绕开优化路径，但这些字段的检索一并变慢 |
| `ZO_ENABLE_INVERTED_INDEX=false` | 核弹级——O2 最大的优势就是全文检索 |

**但三条都要求你事先知道数据的基数分布，而失败是静默的。** LIMIT 扫描已经证明了这一点：没有一个值能保证正确，只有「错得少一点」和「错得多一点」。

所以严格说，这不是「有临时解法的 bug」，而是：

> **一个可以降低触发概率、但无法确认是否已经规避的正确性缺陷。**

对于要拿聚合结果做告警阈值、容量决策或对外报表的场景，「我调了参数应该没问题了」和「我能验证结果是对的」，不是一回事。

##### 实际杀伤面

按**日志级别、服务名、状态码、事件类型**分组，是可观测性里最基本的查询。而 `index_fields` 恰恰就是官方建议给这类低基数枚举字段配的。

**两个推荐做法叠加，产出静默错误的结果，而且查询范围越大错得越离谱。**

「查最近 30 天各服务的错误分布」——这种再普通不过的看板查询，你会拿到一个少了 70%、缺了 9 个类别的图表，**没有任何警告**。而且因为它总是稳定地返回同一个错误答案，你甚至不会因为数字跳动而起疑。

另有 2 个全文 token 场景（`body` 含 `error`：CK 78,852 vs O2 100,068；event_type + token：26,269 vs 32,505）因 CK `hasAnyTokens` 与 O2 `match_all` 的 tokenizer/大小写边界不同而结果不等，**这属于语义差异不属于错误**，可比耗时但不参与胜负判定。

**所以最终参与排名的是 24 个场景。**

#### 单查询延迟：首次触达差 4 倍，缓存热了收敛到 1.4 倍

| 指标（首次触达，仅关闭结果缓存） | ClickHouse | O2 本地 | O2 S3 |
|---|---:|---:|---:|
| 场景胜出数（24 个） | **14** | 3 | 7 |
| 24 场景累计墙钟 | **11.33 s** | 82.24 s | 29.49 s |
| 每场景中位耗时比 | 1.00× | **4.28×** | 1.25× |
| 几何平均耗时比 | 1.00× | 3.65× | 1.59× |

| 指标（同范围重复，文件缓存转热） | ClickHouse | O2 本地 | O2 S3 |
|---|---:|---:|---:|
| 场景胜出数（23 个） | **11** | 5 | 7 |
| 累计墙钟 | **4.98 s** | 9.87 s | 7.22 s |
| 每场景中位耗时比 | 1.00× | **1.39×** | 1.13× |
| 几何平均耗时比 | 1.00× | 1.25× | 1.10× |

两件事值得单独拎出来：

1. **O2 的首触达代价很高，热了以后差距大幅收敛**（4.28× → 1.39×）。这与调研篇的源码结论一致：O2 的查询性能高度依赖 `footer_cache` 预热与本地文件缓存，**冷路径要下载并解析 Parquet footer、warm up Tantivy term**。
2. **「O2 S3 比 O2 本地快」是个陷阱，不要照抄**。表面上 S3 端（1.25×）明显好于本地端（4.28×），但原因是 **5082 这个流显式配置了精确索引，而 5080 本地流没有配**。这是索引配置差异，不是 S3 比本地盘快。索引配置未对齐，是本轮测试最大的遗留缺口。

**还有一个反直觉的观察**：O2 的加速主要不来自 result cache。24 个场景里只有 6 个达到 `result_cache_ratio=100`，1 个 75%，其余大多为 0——**热态的快是 `cached_ratio` 文件缓存给的**。对照组 CK 是 27 次 QueryCache miss + 135 次 hit，完全吻合 27×(1+5) 的设计。热态 p50 胜出数：CK 17、O2 本地 2、O2 S3 5。

#### 并发吞吐：CK 能吃满 8 并发，O2 聚合 4 并发封顶

单位 QPS，顺序为 `CK / O2 本地 / O2 S3`：

| 场景 | 1 并发 | 4 并发 | 8 并发 |
|---|---:|---:|---:|
| P01 repo 精确点查 | 9.08 / 3.24 / 10.63 | 32.40 / 5.27 / 15.50 | **63.62** / 5.53 / 17.56 |
| A03 月度数值聚合 | 7.43 / 2.18 / 1.06 | 22.28 / 3.74 / 2.10 | **32.37** / 3.75 / 2.19 |
| G01 月度低基数多字段分组 | 7.70 / 3.85 / 1.10 | 22.16 / 5.27 / 2.02 | **31.40** / 5.56 / 2.17 |
| T01 正文子串 | 2.79 / 9.65 / 9.09 | 3.62 / **18.95** / 18.09 | 5.30 / **18.89** / 17.93 |
| D04 offset=100,000 深分页 | 2.61 / 1.74 / 1.67 | 3.51 / 3.14 / 3.29 | 3.96 / 2.95 / 2.79 |

- **CK 的点查从 9.08 扩到 63.62 QPS（7.0 倍）**，数值聚合 7.43 → 32.37（4.4 倍），并发扩展基本线性。
- **O2 的聚合在 4 并发就到平台期**：2.18 → 3.74 → 3.75，第 8 并发几乎只增加单请求延迟。CPU 数据佐证了这一点：O2 从 4 并发到 8 并发，平均 CPU 只从 18.23 核涨到 23.21 核。
- **深分页三家都很差**，O2 在 8 并发下吞吐反而低于 4 并发。生产上应该用 search-after / 游标，而不是继续加大 offset——这条对三个引擎都成立。

#### O2 确实赢的地方：正文子串扫描

这是本轮 O2 唯一一个大幅领先且原因清楚的场景：

```
T01 正文子串，8 并发：
  O2 本地  18.89 QPS
  O2 S3    17.93 QPS
  CK        5.30 QPS      ← O2 快 3.6 倍
```

而且 O2 在 1 并发时就有 9.65 QPS（CK 2.79），4 并发即达平台期。**这正是 Tantivy 倒排索引 + 列式直读的主场**，也是 O2 相对 CK 最有说服力的能力差异。同时要注意 CK 侧的成本：query_log 显示 T01 每请求峰值内存约 1.2–1.25 GiB，这在 CK 上也不是廉价操作。

#### 一个决定性的 caveat：后几轮根本没读 S3

| 阶段 | S3 GET | PUT | 响应体合计 |
|---|---:|---:|---:|
| cache-bypass 首轮 | **12,911** | 2 | 约 1.269 GiB |
| cache-bypass 重复轮 | **0** | 0 | 0 |
| 原生缓存 5 次重复 | **0** | 2 | 近 0 |
| 1/4/8 并发测试 | **0** | 2 | 近 0 |

> ⚠️ **除首轮外，所有「O2 S3」数字测的都是「远端流 + 本地文件缓存」，不是对象存储冷读。** 上面那些热态和并发的 S3 数据，一次 GET 都没发出去过。真要评估对象存储冷读，必须换隔离的新前缀或可控文件缓存的实例重测。

这恰好从实测侧印证了调研篇的源码判断：**O2 在对象存储上的查询性能，本质是一场缓存命中率游戏。** 缓存命中时它能和本地盘引擎五五开；一旦落到冷路径（新时间范围、缓存被挤出、节点重启、一致性哈希重分布），首触达 4.28× 的代价就会重新出现。

另外，`.95` 那台机器的 `/dev/sda` 在各阶段仍保持约 97%–100% util，但热态和并发阶段抓包为 0 GET、仅 2 次 PUT——**这段磁盘饱和不能归因于前台查询**，更可能来自 RustFS/O2 后台工作或同盘其他负载，要进程级块 I/O 或 eBPF 才能最终归因。

#### 查询侧资源消耗

| 引擎 | 并发 | O2 CPU 平均 | O2 CPU 峰值 | O2 RSS 峰值 |
|---|---:|---:|---:|---:|
| O2 本地 | 1 | 8.75 核 | 28.57 核 | 3.46 GiB |
| O2 本地 | 4 | 18.23 核 | 39.61 核 | 5.71 GiB |
| O2 本地 | 8 | 23.21 核 | 43.05 核 | 6.07 GiB |
| O2 S3 | 8 | 19.82 核 | 33.40 核 | 5.18 GiB |

值得注意的对照：**O2 写入时只吃得动约 4 核（§2.3），查询时却能瞬时冲到 43 核。** 说明 DataFusion 的查询并行度是正常工作的，写入侧的 CPU 上不去确实是上游 HTTP/JSON 解析链路的问题，而不是 O2 整体不会用多核。O2 的内存峰值来源是深分页 D04（6.07 GiB）。

#### 查询性能小结

| 维度 | 结论 |
|---|---|
| **正确性** | 🔴 **GROUP BY 字段配为 `index_fields` 时，聚合结果静默残缺**——实测 12 个分组只返回 3 个、行数少 **70.67%**，且 `is_partial=false`。跨文件越多越严重，提高 LIMIT 无安全阈值。**与存储后端无关，v0.93.0 仍未修复** |
| **单查询·冷** | CK 胜（24 场景赢 14）；O2 本地中位 **4.28×**、O2 S3 **1.25×** |
| **单查询·热** | 差距收敛，O2 本地 **1.39×**、O2 S3 **1.13×**；但 O2 的快主要来自文件缓存而非 result cache |
| **并发扩展** | **CK 明显更强**：点查 7 倍线性扩展；**O2 聚合 4 并发封顶** |
| **O2 强项** | **正文子串扫描快 CK 3.6 倍**（8 并发 18.89 vs 5.30 QPS） |
| **深分页** | 三家都差，必须改用 search-after/游标 |
| **最大缺口** | 5080/5082/CK 索引配置未一一对应；S3 冷读未真正测到（重复轮 0 GET） |

## 附：可复现性与测量口径

- **数据**：两份都是公开数据集，**不含任何生产数据**——§1 是 OpenObserve 官方 k8s 日志样例（8.40 MiB），§2 是 ClickHouse 官方 GitHub Events 示例数据集（27.3 亿行 / 54 列）。**两边都不是自家产品的「主场数据」，各自都拿了对方的公开数据来打，这是本文选型的刻意安排。**
- **压缩率口径**：原始未压缩大小 ÷ 落盘大小（含索引时明确标注）。
- **O2**：用 **`compressed_size` + `index_size`**（UI 的「实际存储」+「索引大小」）。
  > ⚠️ **千万别用 `storage_size`**。这个字段名极具误导性——源码里 `self.storage_size += meta.original_size`，它累加的是 `original_size`（**flatten 之后的记录重新 `serde_json::to_vec()` 得到的 JSON 文本字节数**，UI 显示为「采集数据 / Ingested Data」），**与落盘大小无关**。用错这个字段，会把 174.64 GiB 误读成 3.08 TiB。
- **CH**：`SELECT sum(bytes_on_disk) FROM system.parts WHERE active`（**含二级索引**）。
  > ⚠️ 只看 `system.columns` 的 `data_compressed_bytes` 会**漏掉全文索引体积**——我们在这次实测中真踩过这个坑，一度据此得出完全相反的结论。

> **两边的统计口径都有坑，而且坑的方向相反**：O2 容易把「未压缩的 JSON 文本」当成存储量（虚高），CH 容易漏算索引（虚低）。这也是为什么本文坚持只比**绝对落盘字节数**、且明确标注每个数字的取数字段。
- **查询口径**（§2.8）：
  - CK 关闭 query result cache；每次 O2 cache-bypass 查询前删除该流结果缓存。**未执行 `drop_caches`**，因此「首次触达」只描述观测到的缓存状态，**不等于物理冷盘**。
  - 三引擎串行执行单查询、按场景轮转；并发测试每次只压一个引擎。
  - 明细与分页使用稳定复合排序，结果做规范化摘要逐字段校验——**这是发现 G02 正确性异常的前提**。跨引擎压测如果只比耗时不比结果，会把一个正确性 bug 当成「O2 聚合还挺快」。
  - > ⚠️ 索引配置不对齐的代价比想象的大。本轮 5082 配了精确索引、5080 没配，这个缺口不仅影响性能可比性，还**制造了一个「S3 专有缺陷」的假象**——直到追进源码才发现真正的变量是 index_fields，不是存储后端。**跨端对比时，索引配置必须一一对应，否则你不知道自己在比什么。**
  - > ⚠️ 比查询前先 EXPLAIN 确认索引真的命中。`ILIKE` 在 CK 上从不走全文索引，用它测出的任何「O2 快 N 倍」都是在和全表扫描比。
- **公平性四原则**：同数据、同 zstd level、功能对等（索引对齐）、口径一致。详见调研篇附录 C 的《O2 vs ClickHouse 公平对比 SOP》。
  > 本轮查询测试**没有完全做到第三条**：O2 5082（S3）配置了精确索引而 5080（本地）没有，所以 §2.8 里「O2 S3 比 O2 本地快」不能作为结论输出。这是本轮已知的最大公平性缺口，如实记录在此。
