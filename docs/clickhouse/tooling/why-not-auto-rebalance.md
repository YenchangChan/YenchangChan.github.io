# 扩容之后为什么不自动做数据均衡

<!-- 【这篇横跨两栏：入口是选型争议，落点是产品决策。流量最好的一篇。】

## 一、一个流行的批评
  "CK 扩容不会自动均衡，Doris 会，所以 Doris 更成熟。"

## 二、真正的差异不是成熟度，是架构假设
  Doris：分桶规则由引擎管，引擎知道 hash 规则 → 自动均衡是安全的
  ClickHouse：sharding 常常由业务决定（写入端自己选分片）→ 引擎不知道语义

  这不是能力差距，是两者对「sharding 所有权」的假设不同。

## 三、所以自动 rebalance 不是"能不能"的问题
  ① 有些数据按业务 id 做 sharding，自动搬迁会让数据全错
  ② 而且是【静默地错】—— 不报错、不失败、查询照常返回，只是答案不对。
     没人知道它从哪天开始错的。
  ③ 最关键：做这个决定需要的信息（业务的 sharding 语义），
     不在做决定的那一层。存储层只看得见 parts 和分片，
     它永远不可能知道自己安不安全。
     → 这不是实现得不够好，是层次边界问题，再怎么做也解决不了。

  【顺序注意】这一节必须放在"可审计"前面。
  它是普适的技术论证，互联网读者也秒懂；
  "要可审计"放前面容易被读成传统企业的包袱。

## 四、即使在语义安全的场景，我也不自动做
  每一步操作都要可审计、可追溯，不能是黑盒。
  数据搬迁是不可逆的，运维需要知道：搬什么、搬到哪、搬之前什么样。
  → 这一节从"不得不"变成"即使可以我也不"，那才是取舍。

## 五、所以 ckman 怎么做的
  提供均衡能力，但由人触发；
  配前置检查、执行计划预览、风险确认。
  不是"点了就跑"，是"看清楚再点"。

## 六、一条可推广的原则
  技术上可做 ≠ 应该做。
  当做决定所需的信息不在做决定的那一层时，自动化就是在赌。
